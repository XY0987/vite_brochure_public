# 01 · 插件开发：从最小插件到完整生命周期与常用钩子

> 本节解决的真实工程问题：项目里总有些活儿没有现成插件能干——给所有模块注入一段环境变量、把一个约定路径变成「虚拟模块」、在 dev server 上加一个 mock 接口、构建时往 `index.html` 注入埋点脚本、改某类文件时做自定义热更新。这些都得自己写插件。但一上手就懵：插件到底是个啥？有哪些钩子？哪些钩子 dev 才跑、哪些 build 才跑？`enforce`、`apply` 是干嘛的？本节带你从「一个对象」开始，把 Vite 插件的钩子体系和执行时机一次讲清，让你写插件时心里有张完整的「时序图」。

事实基线：2026 年中，Vite 8.x（默认 Rolldown 打包器、Oxc 转译）。

---

## 一、最小插件：插件就是一个对象

先破除神秘感。一个 Vite 插件，**本质上就是一个带 `name` 字段、外加若干「钩子函数」的普通 JS 对象**（通常用一个返回该对象的工厂函数包起来，方便传参）。

最小到不能再小的插件长这样：

```js
// vite.config.js
import { defineConfig } from 'vite';

function helloPlugin() {
  return {
    name: 'hello-plugin',          // 必填，报错/调试时用来标识是哪个插件
    transform(code, id) {
      // 给每个 .js 模块开头加一行注释（仅作演示）
      if (id.endsWith('.js')) {
        return `// touched by hello-plugin\n${code}`;
      }
    },
  };
}

export default defineConfig({
  plugins: [helloPlugin()],
});
```

就这么简单。`plugins` 数组里的每一项就是一个这样的对象。你在 [02 章手写的迷你框架插件](../02-框架集成与测试/01-框架插件集成机制.md) 就是这个套路——只挂了一个 `transform` 钩子。

> 关键认知：**Vite 自己的绝大部分功能（CSS 处理、别名解析、HMR、依赖预构建的接入……）也是用这套插件机制实现的内部插件。** 你写的插件和 Vite 内部插件是「同一种东西」，只是执行顺序不同（见第四节 `enforce`）。

## 二、钩子分两类：Vite 特有钩子 vs Rollup 通用钩子

插件能挂的钩子分成两大阵营，搞清这个分类，后面所有时机问题都好理解：

| 类别 | 代表钩子 | 谁定义的 | 何时跑 |
|---|---|---|---|
| **Rollup 通用钩子** | `resolveId`、`load`、`transform`、`buildStart`、`renderChunk`、`generateBundle` | Rollup（Vite 借用） | dev 时由 Vite 模拟调用；build 时由 Rollup/Rolldown 调用 |
| **Vite 特有钩子** | `config`、`configResolved`、`configureServer`、`transformIndexHtml`、`hotUpdate` | Vite 自己 | 只在 Vite 流程里跑 |

这一节先把每个常用钩子干嘛的过一遍，下一节讲执行顺序。**为什么有「Rollup 通用钩子」这一类、它和 Vite 是什么关系，是 [02 节](./02-Rollup基础钩子模型与Vite的关系.md) 的主题**，这里只需先知道：`resolveId / load / transform` 这套「构建钩子」是从 Rollup 借来的，dev 和 build 都会跑。

### Rollup 通用钩子（构建主链路 + 输出阶段）

- **`buildStart` / `buildEnd`**：构建开始/结束的钩子，适合做初始化、清理。
- **`resolveId(source, importer)`**：解析模块 ID。返回一个字符串就表示「这个 import 由我来定位」。常用于实现虚拟模块、重定向 import。
- **`load(id)`**：根据 ID 给出模块内容。返回代码字符串就表示「这个模块的内容由我提供」（典型场景：虚拟模块的内容、从非文件来源加载）。
- **`transform(code, id)`**：拿到模块源码做改写，返回新代码（和 sourcemap）。**最常用**的钩子——编译、注入、替换都在这。
- **`renderStart`**：打包输出阶段开始时调用。适合在正式生成 chunk 前做最后的准备。
- **`renderChunk(code, chunk)`**：每个 chunk 生成后调用，可以改写最终要输出的 chunk 代码。常用于 banner/footer、产物级替换、包装代码。
- **`generateBundle(options, bundle)`**：产物清单生成后、写入磁盘前调用，可以新增、删除、修改输出文件。常用于生成 manifest、额外资源、调整文件名。
- **`writeBundle`**：产物已经写入磁盘后调用。适合做构建后的通知、上传、清理等副作用。

### Vite 特有钩子

- **`config(config, env)`**：在配置被解析「之前」介入，返回一个对象会被深合并进用户配置。用来由插件帮用户补默认配置（如声明要预构建的依赖）。
- **`configResolved(resolvedConfig)`**：配置最终敲定后回调，拿到只读的完整配置存起来后用（比如根据 `command === 'build'` 决定行为）。
- **`configureServer(server)`**：**只在 dev** 调用，拿到 dev server 实例，最常见用途是加自定义中间件（mock API、自定义路由）。
- **`transformIndexHtml(html)`**：专门改 `index.html`，可注入脚本/标签。
- **`hotUpdate(options)`**：**只在 dev** 调用，文件变更时介入 HMR，自定义「这次变更要更新哪些模块 / 要不要整页刷新」。旧版本常见的 `handleHotUpdate` 仍有兼容分支，但新插件建议写 `hotUpdate`。

## 三、执行时机：dev 和 build 跑的钩子不一样

这是初学者最容易翻车的地方——**很多钩子只在某个阶段跑**。把下面这张「时序」记住，你就不会再写出「为什么我的 `generateBundle` 在 dev 里没触发」这种困惑。

```
通用（dev + build 都有）
  config → configResolved → buildStart → resolveId/load/transform（按模块反复调用）

dev 独有（vite / vite dev）
  configResolved 之后：configureServer（建 dev server，加中间件）
  运行期：每个请求触发 resolveId → load → transform
  改文件：hotUpdate

build 独有（vite build）
  模块图构建完：renderStart → renderChunk（每个 chunk）→ generateBundle → writeBundle
  （这些「输出阶段」钩子 dev 根本不会跑，因为 dev 不产出 bundle）
```

记住两条结论：

1. **`resolveId / load / transform` 两个阶段都跑**——所以你写的转换逻辑 dev 预览和 build 产物里行为应当一致（这正是 Vite 想要的「dev/build 同源」）。
2. **`renderChunk / generateBundle / writeBundle` 只在 build 跑**——它们操作的是「打包后的产物 chunk」，dev 不打包，自然没有。反过来 `configureServer / hotUpdate` 只在 dev 跑。

> 排查口诀：钩子没触发？先问「它属于 dev 独有、build 独有、还是通用」——大半的「钩子不执行」都是阶段搞错了。

## 四、enforce 与 apply：控制插件的位置和生效阶段

一个项目里十几个插件，谁先跑谁后跑会直接影响结果（比如你想在框架插件「编译之前」改源码，就必须排在它前面）。两个字段控制这件事：

### `enforce`：插件排在哪一批

Vite 把插件分成三批顺序执行：

```
1. enforce: 'pre' 的用户插件
2. Vite 核心插件（一部分）
3. 普通用户插件（没写 enforce）
4. Vite 构建用插件
5. enforce: 'post' 的用户插件
```

```js
function myPlugin() {
  return {
    name: 'my-plugin',
    enforce: 'pre',   // 'pre' | 'post' | 不写（默认中间批）
    transform(code, id) { /* ... */ },
  };
}
```

- 想**在别的插件（含框架插件）处理之前**就拿到原始源码 → `enforce: 'pre'`。
- 想**在所有处理之后**收尾（比如对最终产物做统计） → `enforce: 'post'`。

### `apply`：插件只在某个命令生效

有些插件只该在 build 跑（比如产物压缩、可视化分析），有些只该在 dev 跑（比如 mock 服务）。用 `apply` 限定：

```js
function onlyBuildPlugin() {
  return {
    name: 'only-build',
    apply: 'build',   // 'build' | 'serve'；也可传函数做更细判断
  };
}
```

也可以传函数，按配置/命令动态决定：

```js
apply(config, { command }) {
  // 只在 build 且不是 SSR 时启用
  return command === 'build' && !config.build?.ssr;
}
```

> 实战意义：很多「dev 正常、build 出问题」或反过来的诡异现象，根因就是某个插件 `apply` 限定错了，或 `enforce` 顺序导致两个插件互相覆盖。排查第三方插件时，先看它声明的 `enforce`/`apply`。

## 五、实战钩子之一：虚拟模块（resolveId + load 配合）

「虚拟模块」是插件开发里极高频的模式：你想让代码里能 `import` 一个**磁盘上根本不存在的模块**，内容由插件动态生成（如把构建时间、Git 信息、路由表注入进来）。

实现靠 `resolveId` + `load` 两个钩子配合，外加一个约定俗成的 `\0`（空字符）前缀（告诉其它插件「这是虚拟模块，别去文件系统找它」）：

```js
function virtualInfoPlugin() {
  const virtualId = 'virtual:build-info';
  const resolvedId = '\0' + virtualId;   // \0 前缀是 Rollup/Vite 的约定

  return {
    name: 'virtual-build-info',
    resolveId(id) {
      if (id === virtualId) return resolvedId;  // 认领这个 import
    },
    load(id) {
      if (id === resolvedId) {
        // 返回这个虚拟模块的「源码」
        return `export const builtAt = ${JSON.stringify(new Date().toISOString())};`;
      }
    },
  };
}
```

业务代码里就能这样用：

```js
import { builtAt } from 'virtual:build-info';
console.log('构建于', builtAt);
```

> 这就是 `vite-plugin-pwa`、各类「自动路由」插件的底层套路——把生成的内容包装成一个虚拟模块给你 import。

## 六、实战钩子之二：configureServer 加中间件（dev mock）

`configureServer` 拿到的是 dev server 实例，它内部是一个 [Connect](https://github.com/senchalabs/connect) 中间件栈，你可以 `server.middlewares.use(...)` 加自己的中间件——最常见就是 dev 阶段 mock 一个 API，省得起后端：

```js
function mockApiPlugin() {
  return {
    name: 'mock-api',
    apply: 'serve',   // 只 dev 需要
    configureServer(server) {
      server.middlewares.use('/api/hello', (req, res) => {
        res.setHeader('Content-Type', 'application/json');
        res.end(JSON.stringify({ msg: 'hello from mock', ts: Date.now() }));
      });
    },
  };
}
```

启动 dev 后访问 `/api/hello` 就能拿到 mock 数据。`vite-plugin-mock` 等就是把这套封装得更好用。

## 七、实战钩子之三：transformIndexHtml 改 HTML

`index.html` 是 Vite 的入口，但它不是普通静态文件——Vite 会用 `transformIndexHtml` 这一专门钩子让插件改它（注入脚本、meta、CDN 标签等）。返回值支持「返回 HTML 字符串」或「返回要注入的标签描述对象数组」两种形式：

```js
function injectScriptPlugin() {
  return {
    name: 'inject-script',
    transformIndexHtml(html) {
      return {
        html,
        tags: [
          {
            tag: 'script',
            children: `console.log('注入的内联脚本')`,
            injectTo: 'head',   // head | body | head-prepend | body-prepend
          },
        ],
      };
    },
  };
}
```

这种「描述对象」写法比手动字符串拼接 `</head>` 安全得多，是官方推荐姿势。

## 八、实战钩子之四：hotUpdate 自定义 HMR

默认情况下 Vite 沿模块图自动决定热更新边界（见 [02 章 HMR 退化](../02-框架集成与测试/01-框架插件集成机制.md)）。但对某些自定义文件类型，你想自己掌控「改了它要更新谁」，就用 `hotUpdate`。`handleHotUpdate` 是旧插件 API 的兼容钩子，读旧文章或旧插件时会见到它，新代码优先用 `hotUpdate`：

```js
function customHmrPlugin() {
  return {
    name: 'custom-hmr',
    hotUpdate({ file }) {
      if (this.environment.name !== 'client') {
        return;
      }
      if (file.endsWith('.data.json')) {
        // 例：数据文件变了，主动通过 WebSocket 通知客户端做自定义处理
        this.environment.hot.send({
          type: 'custom',
          event: 'data-update',
          data: { file },
        });
        return [];   // 返回空数组 = 我已处理，别走默认 HMR
      }
      // 不返回 = 走 Vite 默认逻辑
    },
  };
}
```

返回值语义很关键：返回模块数组 → 用这些模块做更新；返回空数组 → 「我接管了，别再默认处理」；不返回 → 走默认。

## 九、动手：一个把上面钩子都用上的插件

光看片段容易散。配套 demo 把本节几个钩子**集成到一个真实可跑的项目里**，你能在浏览器和构建日志里同时看到它们生效。

配套代码：[第一阶段-使用篇/03-插件与生态/01-插件开发/](https://github.com/XY0987/vite_brochure_code_public/tree/main/第一阶段-使用篇/03-插件与生态/01-插件开发/)

```bash
cd vite_brochure_code_public/第一阶段-使用篇/03-插件与生态/01-插件开发
npm install
npm run dev      # 体验 虚拟模块 / mock 中间件 / HTML 注入 / 自定义 HMR
npm run build    # 看 build 独有钩子（generateBundle 等）打印的日志
```

观察点：

1. 页面上显示的「构建/启动时间」来自 `import 'virtual:build-info'`——一个磁盘上不存在的**虚拟模块**（`resolveId`+`load`）。
2. 页面发起 `/api/hello` 请求拿到 mock 数据——来自 `configureServer` 加的中间件（`apply: 'serve'`，build 不生效）。
3. `index.html` 的 `<head>` 里多了一段注入脚本——来自 `transformIndexHtml`。
4. 改 `src/notes.txt`（一个自定义文本）→ 控制台打印自定义 HMR 消息，而不是整页刷新——来自 `hotUpdate`。
5. 跑 `npm run build`，终端能看到 `buildStart` / `generateBundle` 打印的日志；而 `configureServer` 的日志不会出现——**亲眼验证「dev 独有 vs build 独有」**。
6. demo 里两个插件分别用了 `enforce: 'pre'` 和默认顺序，控制台按顺序打印 `transform`，验证执行次序。

## 十、本节小结

- 插件就是一个 `{ name, ...hooks }` 对象；Vite 自身功能也是用同一套插件机制实现的。
- 钩子分两类：**Rollup 通用钩子**（`resolveId/load/transform` 等，dev+build 都跑）和 **Vite 特有钩子**（`config/configureServer/transformIndexHtml/hotUpdate` 等）。
- 时机是重点：`configureServer`/`hotUpdate` 只 dev 跑；`renderChunk`/`generateBundle`/`writeBundle` 只 build 跑；`resolveId/load/transform` 两边都跑。
- `enforce`（pre/post）控制插件排在哪一批，`apply`（serve/build）控制只在哪个命令生效——很多「dev/build 行为不一致」根因在这两个字段。
- 高频模式：虚拟模块（`resolveId`+`load`+`\0` 前缀）、dev mock（`configureServer` 中间件）、HTML 注入（`transformIndexHtml`）、自定义热更新（`hotUpdate`）。

## 十一、可直接用于项目的 checklist

- [ ] 写插件先确定要挂的钩子属于「通用 / dev 独有 / build 独有」哪一类，避免在错误阶段找钩子。
- [ ] 插件一定写清晰的 `name`，报错和 `--debug` 日志才认得出是谁。
- [ ] 需要在框架/其它插件之前处理源码 → 加 `enforce: 'pre'`；收尾统计 → `enforce: 'post'`。
- [ ] 只在某阶段生效的插件（mock、压缩、分析）务必加 `apply: 'serve' | 'build'`，否则会在不该跑的阶段拖慢或报错。
- [ ] 实现虚拟模块时记得 `resolveId` 返回值加 `\0` 前缀，并在 `load` 里匹配同一个 ID。
- [ ] 改 `index.html` 用 `transformIndexHtml` 的 `tags` 描述对象，别手动字符串拼接闭合标签。
- [ ] 自定义文件类型的热更新用 `hotUpdate`，明确返回值语义（数组 / 空数组 / 不返回）。
