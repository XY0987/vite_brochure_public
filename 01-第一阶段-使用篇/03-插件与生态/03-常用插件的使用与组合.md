# 03 · 常用官方 / 社区插件的使用与组合

> 本节解决的真实工程问题：新项目的 `vite.config` 里往往躺着一长串插件，新人接手时一脸懵——这些到底各干嘛、能不能删、为什么顺序是这样、为什么换个顺序就报错或产物不对？更现实的是：当你要给项目加能力（自动导入、SVG 组件、PWA、产物分析、压缩、`tsconfig` 路径……），该选哪个插件、放数组哪个位置、要不要加 `enforce`/`apply`？本节给你一份「该装什么」的实战清单，并重点讲清最容易踩的一件事——**插件的组合与顺序**。

事实基线：2026 年中，Vite 8.x。下文版本号为示意，实际以你安装时的最新版为准。

---

## 一、官方核心插件：先认清「框架插件之外」还有什么

[02 框架集成](../02-框架集成与测试/README.md) 已经讲过框架插件（`@vitejs/plugin-vue` / `-react` / `-react-oxc` 等）。官方维护的插件里，还有一个绕不开的：

### `@vitejs/plugin-legacy`：给老浏览器兜底

Vite 默认只产出现代 ESM 产物（面向支持 `<script type="module">` 的浏览器）。若你的用户里还有老浏览器，用它额外产出一套带 polyfill 的 legacy 包：

```js
import legacy from '@vitejs/plugin-legacy';

export default defineConfig({
  plugins: [
    legacy({
      targets: ['defaults', 'not IE 11'],
    }),
  ],
});
```

它**只在 build 生效**（内部声明了 `apply: 'build'`）——这正是 [01 节 `apply`](./01-插件开发从最小插件到完整生命周期.md) 的典型应用：dev 用现代浏览器，没必要降级。

## 二、高频社区插件清单（按用途）

社区插件成千上万，下面是真实项目里复用率最高的一批，按「解决什么问题」归类。**记住它们的用途和「该排在什么位置」比记 API 更重要**。

| 插件 | 解决的问题 | 关键点 |
|---|---|---|
| `vite-tsconfig-paths` | 让 `tsconfig.json` 里的 `paths` 别名在 Vite 里直接生效，不用在 `resolve.alias` 再写一遍 | 解析类，建议靠前；**Vite 8 起已内置 `resolve.tsconfigPaths`，新项目优先用内置**（见下方说明） |
| `unplugin-auto-import` | 自动 import 常用 API（`ref`、`useState`…），少写 import | 生成类型文件，需 `enforce: 'pre'` 之类靠前位置 |
| `unplugin-vue-components` | 组件库（如 Element/Antd）按需自动导入组件 | 同上 |
| `unplugin-icons` | 把图标当组件直接用 | unplugin 系列，跨构建工具通用 |
| `vite-plugin-svgr` / svg 类 | 把 `.svg` 当 React/Vue 组件导入 | 影响 `transform`，注意与框架插件顺序 |
| `vite-plugin-pwa` | 一键接入 PWA（Service Worker、manifest） | 内部用虚拟模块 + Output 钩子 |
| `rollup-plugin-visualizer` | 构建产物体积可视化分析 | **Output 阶段**钩子，`apply: 'build'`，通常排最后 |
| `vite-plugin-compression2` | 构建时生成 `.gz`/`.br` 预压缩产物 | 同为 build 期、排在产物生成之后 |

> 选型小原则：**优先选 `unplugin-*` 系列**（一套代码同时支持 Vite/Rollup/webpack/esbuild），生态活跃、跨工具迁移成本低；其次选明确标注「支持 Vite 8 / Rolldown」的插件，避开依赖 Rollup 内部实现的老插件（原因见 [02 节](./02-Rollup基础钩子模型与Vite的关系.md)）。

> 一个「插件被内置化」的真实例子：路径别名复用 tsconfig 这件事，早年靠社区插件 `vite-tsconfig-paths`，**Vite 8 已把它内置成 `resolve.tsconfigPaths` 选项**。所以装插件前先看一眼官方文档——你要的能力可能已经内置了。最稳、最通用的别名方式仍是内置的 `resolve.alias`（任何版本都可靠），配套 demo 即用它演示。

## 三、重点：插件的组合与顺序

这是本节的核心，也是最常踩的坑。`plugins` 是个**数组，顺序有意义**。最终执行顺序由两层决定：

1. **`enforce` 分批**（[01 节](./01-插件开发从最小插件到完整生命周期.md) 讲过）：`pre` 批 → 普通批 → `post` 批。
2. **同一批内**：按数组里书写的先后顺序。

### 三条实用排序经验

**经验一：解析/别名类插件靠前。** 像 `vite-tsconfig-paths` 这种影响「模块怎么被解析」的，要在别的插件「按解析结果干活」之前生效，所以放前面（或它本身就声明了 `enforce: 'pre'`）。

**经验二：转换类插件，注意和框架插件的相对位置。** 比如「把 SVG 转成组件」的插件，必须保证转换出的 JSX/SFC 还能被框架插件接着编译——通常它需要排在框架插件**之前**（用 `enforce: 'pre'`），让框架插件拿到的是已经转好的组件代码。装这类插件时**务必看它文档要求的位置**。

**经验三：产物处理类（分析、压缩、legacy）排最后。** 它们工作在 [02 节](./02-Rollup基础钩子模型与Vite的关系.md) 说的 **Output 阶段**，要等产物 chunk 都生成了才动手。`rollup-plugin-visualizer`、压缩插件放数组末尾、且只 `apply: 'build'`。

一个组合示例（注释标了为什么这么排）：

```js
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';
import tsconfigPaths from 'vite-tsconfig-paths';
import svgr from 'vite-plugin-svgr';
import { visualizer } from 'rollup-plugin-visualizer';

export default defineConfig({
  plugins: [
    tsconfigPaths(),          // 解析类，靠前：先让别名生效
    svgr(),                   // 转换类：把 .svg 转成组件（需在框架插件前）
    react(),                  // 框架插件：编译 JSX、注入 Fast Refresh
    visualizer({              // 产物分析：Output 阶段，排最后
      filename: 'dist/stats.html',
    }),
  ],
});
```

> 体感结论：**80% 的「插件互相打架」问题，调一下顺序或加个 `enforce` 就解决了。** 出现「A 插件的处理被 B 覆盖 / 没拿到 B 处理后的结果」，先想顺序，而不是怀疑插件有 bug。

## 四、条件加载：按命令 / 模式动态启用插件

不是所有插件都该无条件启用。`plugins` 数组支持放 `false`/`null`/`undefined`（会被自动过滤掉），于是能用三元表达式按环境裁剪：

```js
export default defineConfig(({ command, mode }) => {
  return {
    plugins: [
      react(),
      // 只在 build 时做产物分析
      command === 'build' && visualizer({ filename: 'dist/stats.html' }),
      // 只在分析模式开压缩，平时不拖慢构建
      mode === 'analyze' && compression(),
    ],
  };
});
```

两种思路，按需选：

- 插件**自身声明了 `apply`**（如 `legacy`、`visualizer` 多数会自带）→ 你直接放数组即可，它自己会在对的阶段跑。
- 插件没声明、或你想要更细的条件 → 用上面的 `command/mode` 三元表达式手动裁剪（`defineConfig` 传函数拿到 `command`/`mode`，见 [03 环境变量与多模式](../01-核心使用/03-devserver构建预览与环境变量多模式.md)）。

## 五、动手：组合多个插件并观察顺序

配套 demo 在一个真实项目里组合了若干插件（含社区真实插件 + 三个自写的「探针」插件），让你**亲眼看到执行顺序、以及顺序如何影响结果**。

配套代码：[第一阶段-使用篇/03-插件与生态/03-常用插件使用与组合/](https://github.com/XY0987/vite_brochure_code_public/tree/main/第一阶段-使用篇/03-插件与生态/03-常用插件使用与组合/)

```bash
cd vite_brochure_code_public/第一阶段-使用篇/03-插件与生态/03-常用插件使用与组合
npm install
npm run build    # 看插件按 enforce 分批 + 数组顺序执行；产物里多出 stats.html 和 .gz
npm run dev      # 看 dev 下哪些插件生效、顺序如何
```

观察点：

1. 三个自写探针插件分别用 `enforce: 'pre'`、默认、`'post'`，构建日志里能清楚看到 **pre 批 → 普通批 → post 批**的执行顺序。
2. 源码用 `@/` 别名（由内置 `resolve.alias` 提供），页面正常显示 `sum(1,2,3)=6`。
3. `rollup-plugin-visualizer` 在 build 后生成 `dist/stats.html`（产物体积可视化）——它是 Output 阶段插件，dev 不生成。
4. `vite-plugin-compression2` 在 `dist` 里额外产出 `.gz` / `.br` 文件——同为 build 期、产物生成之后。
5. 试着把 `vite.config` 里三个探针插件的顺序打乱、或去掉某个 `enforce`，重新 build，对比日志顺序变化——亲手验证「数组顺序 + enforce」如何共同决定执行次序。

## 六、本节小结

- 官方插件除框架插件外，`@vitejs/plugin-legacy` 用于老浏览器兜底（只 build 生效）。
- 高频社区插件按用途记：解析（`vite-tsconfig-paths`）、自动导入（`unplugin-auto-import`/`-vue-components`）、资源（`vite-plugin-svgr`/`unplugin-icons`）、PWA、产物分析（`visualizer`）、压缩（`vite-plugin-compression2`）。优先选 `unplugin-*` 与明确支持 Vite 8 的插件。
- 组合顺序是重点：`enforce` 分三批（pre→普通→post），同批按数组顺序。经验：解析类靠前、转换类注意与框架插件相对位置、产物处理类排最后。
- 条件加载：`plugins` 数组里 falsy 值会被忽略，用 `defineConfig(({command, mode}) => ...)` 配三元表达式按环境裁剪；或依赖插件自带的 `apply`。
- 大部分「插件互相打架」靠调顺序 / 加 `enforce` 解决，而非插件本身有 bug。

## 七、可直接用于项目的 checklist

- [ ] 接手项目先逐个搞清 `plugins` 里每个插件的用途和它为什么排在这个位置，别盲目删改。
- [ ] 选插件优先 `unplugin-*` 系列和明确标注支持 Vite 8 / Rolldown 的版本，避开依赖 Rollup 内部实现的老插件。
- [ ] 解析/别名类（`vite-tsconfig-paths`）放前面；转换类（svg→组件）按文档要求相对框架插件定位，多半要 `enforce: 'pre'`。
- [ ] 产物分析/压缩/legacy 这类 Output 阶段插件放数组末尾，并确认它们只 `apply: 'build'`。
- [ ] 只在特定命令/模式需要的插件，用 `defineConfig` 函数式 + 三元表达式裁剪，避免无谓拖慢 dev 或 build。
- [ ] 遇到「插件效果被覆盖 / 拿不到上游处理结果」，先调顺序和 `enforce`，再怀疑插件本身。
