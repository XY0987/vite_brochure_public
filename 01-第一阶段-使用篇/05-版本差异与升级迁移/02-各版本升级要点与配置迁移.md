# 02 · 各版本升级要点与配置迁移：rollupOptions / manualChunks 怎么改

> 本节解决的真实工程问题：你把项目从 Vite 5/6/7 升到 8，`npm run build` 跑起来一片 `deprecated` 告警，或者直接报某个配置字段不认识。最高频的两个就是——`build.rollupOptions` 提示该换名了、`output.manualChunks` 说有更好的写法。到底**哪些配置必须改、哪些只是改名、哪些不动也能跑**？本节按「Vite 5→6→7→8」逐版本列出升级要点，再把**配置迁移**这件最具体的事讲透：每个改动给出「旧写法 → 新写法」的可复制对照，并用一个 demo 证明「旧写法靠兼容层仍能跑、新写法是当前推荐」。读完你能拿着 checklist 把一份老 `vite.config` 平移到 Vite 8。

事实基线：2026 年中，Vite 8.1.x / Rolldown 1.1.x。配置字段的废弃与改名以本地实测为准（见末尾「动手」一节，强烈建议自己跑一遍看告警）。

> 前置：建议先读 [01 两条演进主线与版本全景](./01-两条演进主线与版本全景.md)，理解「架构线」与「打包器线」的分工——本节绝大多数配置迁移都来自「打包器线」（Rollup → Rolldown）。

---

## 一、升级的总原则：兼容层兜底，按线推进

Vite 8 不是推倒重来。它带了一层**兼容层**：老的 `rollupOptions`、大部分 Rollup 风格插件、`manualChunks` 等仍然能跑，只是被标记为 deprecated。这给了你一个轻松的迁移姿势：

> **先让项目在 Vite 8 上「能跑」（靠兼容层），再逐项把 deprecated 写法换成新名，最后清理废弃特性。** 不要追求「一步到位改完所有配置」，那样风险集中、不好定位。

按「两条主线」拆解升级要点，思路最清晰：

- **打包器线的迁移**（占绝大多数）：`rollupOptions → rolldownOptions`、`manualChunks → codeSplitting`、个别 Rollup 内部 API 依赖型插件失效。
- **架构线的迁移**：基本无痛——Environment API 向后兼容，纯 SPA / 传统 SSR 几乎不用动。
- **运行环境的硬要求**：Node 版本（Vite 7 起要求 20.19+/22.12+）、已删除的废弃特性。

## 二、逐版本升级要点

下面按「你当前在哪个版本」给出跨版本升级时各自要注意的事。升级是可叠加的——从 Vite 5 升 8，下面 5→6、6→7、7→8 的要点都要过一遍。

### Vite 5 → 6（架构线质变，但向后兼容）

- **核心变化**：引入 Environment API（见使用篇 [04 多环境章](../04-多环境与工程化场景/01-EnvironmentAPI落地多环境多运行时.md)）。这是大规模内部重构，但**官方承诺向后兼容**。
- **你要做的**：多数项目**几乎不用改**。如果你之前用 `ssrLoadModule`、自定义 SSR 中间件等较底层 API，对照迁移指南确认有没有签名调整；`ssrLoadModule` 在 Vite 8 仍可用，但已进入 future deprecation 路径，底层替代方向是 Environment Runner / Module Runner。
- **风险等级**：低。重构在内部，用户态 API 大体不变。

### Vite 6 → 7（清理废弃特性 + 抬高 Node 门槛 + 打包器试水）

- **Node 版本门槛抬高到 20.19+ / 22.12+**。这是硬要求——Node 18 会安装报错或运行异常。**升级前先升 Node**。
- **清理了一批早已废弃的特性**：升级前用 `npm run build` 跑一遍，把告警里点名的废弃项处理掉。
- **可选：试水 Rolldown**。Vite 7 提供 `rolldown-vite` 作为 drop-in，想提前验证 Rolldown 兼容性的团队可以在这一步先试（用法见本章 [04 节 企业升级实战](./04-企业升级实战-从Vite5渐进升级.md)）。不试也完全没问题，默认仍是 esbuild+Rollup。
- **风险等级**：中。主要风险在 Node 门槛和废弃特性，配置层面不大。

### Vite 7 → 8（打包器换血：Rollup → Rolldown）

这是配置迁移的重头戏，绝大多数改动集中在这里：

- **打包器变成 Rolldown**（默认且唯一），dev/build 统一，Oxc 接管转译/压缩。
- **配置字段改名**（兼容层仍支持旧名，但建议改）：`build.rollupOptions → build.rolldownOptions`、`output.manualChunks → output.codeSplitting`（详见第三节）。
- **CJS/ESM 互操作行为对齐 esbuild**：Vite 8 用 Rolldown 统一了 dev 预构建与 build 的 CJS 处理，少数依赖旧「不一致行为」的代码可能表现变化。Vite 8 提供 `legacy.inconsistentCjsInterop: true` 让你**临时退回旧行为**用于排查（属于过渡开关，不是长期方案）。

  这里的「对齐 esbuild」说的是 **CJS 依赖转 ESM 时的互操作规则**，不是说 Vite 8 仍由 esbuild 承担主链路。旧版本 dev 里常由 `optimizeDeps` 通过 esbuild 预构建 CJS 依赖，build 里则由 Rollup/CommonJS 逻辑处理同一个依赖；Vite 8 改成 Rolldown 驱动预构建与生产打包，Oxc 接管常规转译/压缩。两条路径收敛后，`default`、命名导出、`__esModule` 等边界写法可能得到不同导入形状，比如 `import foo from 'some-cjs'` 到底拿到函数本身，还是拿到 `{ default: fn }`。
- **个别插件失效**：依赖 esbuild `onLoad`/`onResolve` 的插件、或深度依赖 Rollup 内部实现的插件可能需要换版本或替换（生态影响见第二阶段专题）。
- **风险等级**：中高。配置好改，真正的风险在「插件兼容性」和「构建产物的细微差异」，必须实跑产物对比（见本章 [04 节](./04-企业升级实战-从Vite5渐进升级.md)）。

## 三、配置迁移核心：两个最高频的改名

### 迁移点 1：`build.rollupOptions` → `build.rolldownOptions`

打包器从 Rollup 换成 Rolldown，承载底层打包配置的字段也跟着改名。**语义完全一致，直接改名即可**：

```js
// 旧（Vite 5–7）
export default defineConfig({
  build: {
    rollupOptions: {
      input: { main: 'index.html', admin: 'admin.html' },
      output: { /* ... */ },
    },
  },
});

// 新（Vite 8 推荐）
export default defineConfig({
  build: {
    rolldownOptions: {       // ← 仅改名
      input: { main: 'index.html', admin: 'admin.html' },
      output: { /* ... */ },
    },
  },
});
```

在 Vite 8 里，`rollupOptions` 是 `rolldownOptions` 的 **deprecated 别名**——不改也能跑，但建议改掉以消除告警、对齐未来。

### 迁移点 2：`output.manualChunks` → `output.codeSplitting`（注意中间还有个 `advancedChunks`）

这是**最容易被旧文章带歪**的一个点，因为它的名字演进了两次。务必记住完整链条：

```
manualChunks（函数）   →  Rollup / Vite 5–7 的写法
advancedChunks（对象）  →  早期 Rolldown 引入的声明式写法，现已 deprecated（会告警）
codeSplitting（对象）   →  当前正式名，结构与 advancedChunks 同构
```

很多 2025 年的文章会告诉你「`manualChunks` 改成 `advancedChunks`」——**这在今天已经过时了**。`advancedChunks` 只是 Rolldown 早期的过渡名，现在的正式名是 `codeSplitting`。三者对照：

```js
// 旧写法 ①：manualChunks 函数式（Rollup 风格，Vite 8 兼容层仍支持）
build: {
  rollupOptions: {
    output: {
      manualChunks(id) {
        if (id.includes('node_modules')) return 'vendor';
      },
    },
  },
}

// 过渡写法 ②：advancedChunks（早期 Rolldown，现已 deprecated，别再用）
build: {
  rolldownOptions: {
    output: {
      advancedChunks: { groups: [{ name: 'vendor', test: /node_modules/ }] },
    },
  },
}

// 当前推荐 ③：codeSplitting（Vite 8 / Rolldown 正式名）
build: {
  rolldownOptions: {
    output: {
      codeSplitting: {
        groups: [{ name: 'vendor', test: /node_modules/ }],
      },
    },
  },
}
```

两个要点：

- **写法从「函数回调」变成「声明式规则」**。`manualChunks` 是「给我一个 id，我用 if 判断归哪个 chunk」；`codeSplitting.groups` 是「声明若干组，每组用 `test` 正则匹配模块路径」。后者更易读、更利于工具静态分析，还能配 `minSize`/`maxSize` 等阈值（见 [03 节](./03-Vite8单打包器解锁的新能力.md)）。
- `manualChunks` **与** `codeSplitting` **不要同时写**——同时存在时 `manualChunks` 会被忽略。

> 这正是本小册反复强调的「版本漂移」陷阱：同一个能力，名字在不同版本里换了好几轮。**别照抄旧文章，以你本地安装版本的实测/类型提示为准。**

## 四、其他零散但会咬人的迁移项

- **Node 版本**：Vite 7+ 要求 Node 20.19+ / 22.12+。CI 镜像、本地 nvm、Dockerfile 都要同步升。
- **React 插件升级**：Vite 8 新项目默认用 `@vitejs/plugin-react` v6，它已经用 Oxc 接管 React Refresh transform；旧的 `@vitejs/plugin-react-oxc` 是过渡包，已 deprecated（见 [02 章 React 接入](../02-框架集成与测试/02-React接入与Oxc接管ReactRefresh.md)）。
- **依赖 Rollup 内部实现的插件**：兼容层覆盖的是「Rollup 插件钩子 API」，不覆盖「插件偷偷访问 Rollup 内部数据结构」的情况。这类插件升级后可能静默失效，需逐个验证。
- **CJS 互操作差异**：见第二节 7→8。遇到「某个 CJS 依赖导入后是 `undefined` / `default` 套了一层」时，先用 `legacy.inconsistentCjsInterop` 确认是不是这个原因，再去修依赖导入写法。

## 五、动手：一个项目，新旧两套配置各构建一次

配套 demo 用同一份源码、两份配置（旧 `rollupOptions + manualChunks`、新 `rolldownOptions + codeSplitting`）各构建一次到不同目录，让你亲眼确认「兼容层让旧配置仍可跑，新写法产物等价」。

配套代码：[第一阶段-使用篇/05-版本差异与升级迁移/02-配置迁移对照/](https://github.com/XY0987/vite_brochure_code_public/tree/main/第一阶段-使用篇/05-版本差异与升级迁移/02-配置迁移对照/)

```bash
cd vite_brochure_code_public/第一阶段-使用篇/05-版本差异与升级迁移/02-配置迁移对照
npm install
npm run compare   # 先各构建一次，再对比两份产物的分包结果
```

它会先跑 `build:old`（旧写法 → `dist-old/`）、再跑 `build:new`（新写法 → `dist-new/`），最后对比：

```
=== 旧写法 dist-old/assets ===
  - index-DRct3vYT.js
  - vendor-CRw9XtSc.js
=== 新写法 dist-new/assets ===
  - index-DRct3vYT.js
  - vendor-CRw9XtSc.js
结论：
  旧写法是否产出 vendor chunk：是
  新写法是否产出 vendor chunk：是
  → 两种写法等价；新写法无 deprecation 警告，是 Vite 8 的推荐姿势。
```

观察点：

1. 两份产物的 `vendor` chunk 内容哈希一致（`vendor-CRw9XtSc.js`）——证明新旧写法**功能等价**，迁移不改变产物。
2. 对比 `vite.config.old.mjs` 与 `vite.config.new.mjs` 两个文件，就是一份「最小迁移 diff」：`rollupOptions→rolldownOptions`、`manualChunks(函数)→codeSplitting(声明式)`。
3. 试着把 `vite.config.new.mjs` 里的 `codeSplitting` 改回 `advancedChunks`，重新构建——你会看到 deprecation 告警，亲手验证「`advancedChunks` 已过时」。

## 六、本节小结

- Vite 8 有兼容层兜底：先靠兼容层让项目「能跑」，再逐项改 deprecated 写法，最后清废弃特性——别一步到位。
- 升级按「两条主线」拆：打包器线（Rollup→Rolldown）承载绝大多数配置迁移；架构线（Environment API）基本无痛。
- 两个最高频改名：`build.rollupOptions → build.rolldownOptions`（纯改名）；`output.manualChunks →（advancedChunks 已弃）→ codeSplitting`（从函数式改成声明式）。
- 别信旧文章的「manualChunks → advancedChunks」——今天的正式名是 `codeSplitting`，`advancedChunks` 已 deprecated。
- 真正的风险不在配置（好改），在插件兼容性与 CJS 互操作差异——必须实跑产物对比（见本章 04 节）。

## 七、可直接用于项目的 checklist

- [ ] 升级前先把 Node 升到 20.19+ / 22.12+（本地 + CI + Docker 同步）。
- [ ] 先不改配置，直接在 Vite 8 上 `npm run build`，把所有 deprecation 告警抄下来当迁移清单。
- [ ] `build.rollupOptions` → 改名为 `build.rolldownOptions`。
- [ ] `output.manualChunks` / `output.advancedChunks` → 统一迁移到 `output.codeSplitting`（`{ groups: [{ name, test }] }`）。
- [ ] 确认 `manualChunks` 与 `codeSplitting` 没有同时存在。
- [ ] 逐个验证插件：尤其是 esbuild 插件、依赖 Rollup 内部实现的插件，跑构建看是否静默失效。
- [ ] 遇到 CJS 依赖导入异常，先用 `legacy.inconsistentCjsInterop` 定位，再修导入写法（别把它当长期开关）。
- [ ] 改完用「旧产物 vs 新产物」对比（chunk 数量、体积、入口）验收，而不是只看「构建没报错」。
