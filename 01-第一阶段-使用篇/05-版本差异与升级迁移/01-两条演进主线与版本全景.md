# 01 · 两条演进主线与版本全景：别背版本号，要读懂「为什么这么变」

> 本节解决的真实工程问题：你打开一个项目，`package.json` 写着 `vite: ^5`，同事的新项目是 `^7`，社区文章在聊 Vite 8 的 Rolldown，掘金小册里还有 Vite 4 的写法——**版本一堆、说法打架，到底每个大版本变了什么、为什么变、我该信哪个？** 如果只是死记「Vite 6 加了 Environment API、Vite 8 换了 Rolldown」，下次遇到 `rollupOptions` 报废告警、或者要做选型时你还是抓瞎。本节给你一把「读版本」的钥匙：把 Vite 5→8 的演进拆成**两条独立主线**，理解每条线想解决什么问题、走到了哪一步。读完你看任何一个 Vite 版本号，都能立刻说出它在两条线上各处于什么位置。

事实基线：2026 年中。最新稳定版 Vite 8.x（2026.03 发布），默认打包器 Rolldown（1.0 已于 2026.05 稳定）。本节所有版本结论都标注了对应时间，避免把阶段性事实当永久结论。

> 范围说明：本节是第一阶段第 5 章的总览，只回答「版本怎么演进、我在哪条线的哪个位置」。具体的升级配置改法见 [02 各版本升级要点与配置迁移](./02-各版本升级要点与配置迁移.md)，新能力见 [03](./03-Vite8单打包器解锁的新能力.md)，企业升级与迁移实战见 [04](./04-企业升级实战-从Vite5渐进升级.md)、[05](./05-迁移案例-从webpack到Vite8.md)。

## 一、为什么是「两条主线」而不是一张版本表

新手读 Vite 版本史最容易犯的错，是把它当成「一条线性的功能清单」——v6 加了啥、v7 加了啥、v8 加了啥，背下来。问题是：这些变化其实分属**两件完全不同、且彼此独立**的事，混在一起记必然记乱。

把它们拆开，一切就清楚了：

```
                    Vite 5        Vite 6        Vite 7        Vite 8
                    (2023底)      (2024.11)     (2025.06)     (2026.03)
主线 A 架构抽象 ─────  client/ssr ──> Environment API ──────────────────────>
（怎么组织构建目标）   两条硬编码     「环境」成一等公民，多环境多运行时

主线 B 打包器 ──────  esbuild(dev)  ──────────> rolldown-vite ──> Rolldown
（用什么引擎打包）     +Rollup(build)            可选 drop-in       默认唯一
                     双引擎                     过渡隔离层         单引擎
```

- **主线 A（架构抽象）**：Vite 内部「怎么描述和组织一次构建的目标」。它在 Vite 6 迎来质变——引入 Environment API，把「构建目标」抽象成一等公民「环境」。这条线**和用什么打包器无关**。
- **主线 B（打包器替换）**：Vite「底层用什么引擎做打包」。它在 Vite 7 给出过渡方案（`rolldown-vite` 可选替换），在 Vite 8 完成终局——Rolldown 成为默认且唯一的打包器。这条线**和上层架构抽象无关**。

> 一句话抓住本质：**A 线动的是「Vite 自己的架构」，B 线动的是「Vite 脚下的引擎」。** 两条线各自演进、互不依赖，只是恰好在这几个版本里先后落地。你记不住版本，是因为你把两条线的事揉成了一团。

## 二、主线 A：架构抽象（Environment API，Vite 6 引入）

Vite 5 及以前，Vite 脑子里的「构建目标」只有两个写死的概念：`client`（给浏览器）和 `ssr`（给 Node）。想再来个「给边缘运行时的产物」？没有官方位置，只能 hack。

Vite 6 的 Environment API 把这件事重构成：**「环境（Environment）」是一等公民，**`client`**/**`ssr` **只是两个内置的默认环境**，你可以自定义任意多个（`edge`、`rsc`、`workerd`……），每个环境有独立的模块图、解析规则和产物。

这条主线的关键事实：

- **引入版本：Vite 6（2024.11）**。它是 Vite 6「大规模内部重构但向后兼容」的核心。
- **它解决的问题**：从「一份配置 + 两条硬编码分支」升级到「一份配置 + N 个对等环境」，让多运行时（浏览器 / Node / 边缘）能用统一模型表达。
- **到 Vite 8 已是稳定的一等能力**，但**对纯前端 SPA 完全透明**——你感知不到它的存在，照常 `vite build` 即可。

> 这条线的用法已经在 [第一阶段 04-多环境与工程化场景 / 01](../04-多环境与工程化场景/01-EnvironmentAPI落地多环境多运行时.md) 详细讲过；它的内部实现见第二阶段、设计动因见第三阶段。本章不重复，只需记住：**Environment API 是「架构抽象」主线的里程碑，始于 Vite 6，与打包器换不换没关系。**

## 三、主线 B：打包器替换（Rolldown，Vite 7 引入、Vite 8 默认）

这是这几年 Vite 最大的底层变化，也是本章后面几节的重点。

**Vite 5 的「双引擎」**：dev 阶段用 **esbuild** 做依赖预构建（快，但产物控制弱），build 阶段用 **Rollup** 做生产打包（产物优，但慢）。两套引擎跑两套逻辑，埋了一个长期隐患——**dev 和 build 行为可能不一致**（最典型的就是 CJS/ESM 互操作的细节差异），导致「开发时好好的，一上线就出问题」的诡异 bug。

**Rolldown** 是用 Rust 重写的打包器，目标是**用一个引擎同时统一 dev 和 build**，既要 Rust 的速度，又要消灭双引擎的行为分裂。它的落地分两步：


| 版本     | 时间      | Rolldown 在这一版的状态                                                                                  |
| ------ | ------- | ------------------------------------------------------------------------------------------------- |
| Vite 7 | 2025.06 | 提供 `rolldown-vite` 作为**可选的 drop-in 替换**——想提前尝鲜的人通过包别名换上它，不想换的继续用默认（esbuild+Rollup）。这是一个**过渡隔离层**。 |
| Vite 8 | 2026.03 | Rolldown 成为**默认且唯一**的打包器，dev/build 统一；Oxc（同属 Rust 工具链）接管转译/压缩；构建相比旧版快约 10–30x。                    |


关键事实：

- **Rolldown 1.0 于 2026.05 稳定**（晚于 Vite 8 的 2026.03 首发，符合「先随 Vite 8 落地、再打稳定版本号」的节奏）。
- Vite 8 仍**保留兼容层**：老的 `build.rollupOptions`、Rollup 风格插件大多继续可用（细节与例外见 02 节）。
- **构建快 10–30x 是基准区间，不是保证值**——取决于项目规模、插件、机器。别把它当成永久承诺写进文档。

## 四、版本全景表：每个版本在两条线的坐标

把两条主线叠到版本上，就得到这张「读版本」的总表：


| 版本     | 时间      | 主线 A（架构）               | 主线 B（打包器）                                                   | 一句话定位       |
| ------ | ------- | ---------------------- | ----------------------------------------------------------- | ----------- |
| Vite 5 | 2023 底  | client/ssr 双硬编码        | esbuild(dev) + Rollup(build) 双引擎                            | 企业现役主力，最稳   |
| Vite 6 | 2024.11 | **Environment API 引入** | 仍是双引擎                                                       | 架构质变、向后兼容   |
| Vite 7 | 2025.06 | Environment API 成熟     | `rolldown-vite` **可选 drop-in**；清理废弃特性；要求 Node 20.19+/22.12+ | 打包器迁移的「试水期」 |
| Vite 8 | 2026.03 | Environment API 稳定     | **Rolldown 默认唯一**；Oxc 接管转译/压缩                               | 单引擎终局       |


读这张表的方法：**先看你在哪个版本，再分别问「我在 A 线哪一步、B 线哪一步」**。例如——

- 「我们用 Vite 5」→ A 线：还没 Environment API；B 线：双引擎，存在 dev/build 不一致风险。升级收益主要来自 B 线提速 + 行为统一。
- 「我们用 Vite 7 + 默认引擎」→ A 线：已具备 Environment API；B 线：还在 Rollup，但**已经可以用** `rolldown-vite` **试水**。这是升 8 前最舒服的「中间站」。

## 五、动手：用版本探针看清你本地到底跑在什么引擎上

不要相信任何文章（包括本节）写的版本号——跑一行命令看你**本地实际安装**的是什么。这是「事实基线」最硬的来源。

配套代码：[第一阶段-使用篇/05-版本差异与升级迁移/01-版本探针/](https://github.com/XY0987/vite_brochure_code_public/tree/main/第一阶段-使用篇/05-版本差异与升级迁移/01-版本探针/)

```bash
cd vite_brochure_code_public/第一阶段-使用篇/05-版本差异与升级迁移/01-版本探针
npm install
npm run info     # 打印 Vite 内部各引擎的真实版本号
npm run build    # 看探针插件确认 build 跑在 Rolldown 上
```

`npm run info` 直接从 `vite` 包里读出四个版本号，在本机（Vite 8.1.0）输出类似：

```
Vite           8.1.0        主框架版本（决定 Environment API / 默认打包器等能力边界）
Rolldown       1.1.3        Vite 8 默认唯一打包器（Rust），同时驱动 dev 与 build
Rollup(兼容)    4.23.0       兼容层报告的 Rollup API 版本，老插件据此判断能力，不再是真打包器
esbuild        0.25.0       历史遗留依赖，Vite 8 转译主力已是 Oxc，这里仅个别场景兜底
```

三个值得你盯住的点：

1. `rolldownVersion` **有值** → 证明 Rolldown 是真打包器。`npm run build` 时探针插件会打印 `command=build → 打包器：Rolldown`，证明 build 也走 Rolldown（不再是 Rollup）。
2. `rollupVersion` **仍有值** → 这是**兼容层报告的版本**，不代表 Rollup 还在做打包。老插件靠它判断「宿主支持哪些 Rollup 能力」，这正是 Vite 8 还能跑大量 Rollup 插件的原因。
3. `esbuildVersion` **仍有值** → esbuild 没被完全删掉，个别转换仍可能兜底；但转译/压缩主力已是 **Oxc**。别再以为「Vite = esbuild」了。

## 六、三个最常见的版本误解，一次澄清

- **误解 1：「Vite 8 还是 esbuild + Rollup」**。错。Vite 8 dev/build 都是 Rolldown，转译/压缩是 Oxc。esbuild/Rollup 仅以「历史依赖 / 兼容层」身份存在。
- **误解 2：「dev 和 build 行为不一致是 Vite 的老毛病，一直都有」**。这是 Vite 5 双引擎时代的问题。Vite 8 单引擎后，dev 的依赖预构建与生产构建共用 Rolldown，CJS 互操作等行为已对齐（Vite 8 甚至提供 `legacy.inconsistentCjsInterop` 开关让你临时退回旧行为以便排查迁移）。
- **误解 3：「**`rolldown-vite` **和 Vite 8 是两个东西，要二选一」**。不是。`rolldown-vite` 是 **Vite 7 时代的过渡 drop-in**——在 Rolldown 还没成为默认时，让你提前换引擎的隔离层。到了 Vite 8，Rolldown 已是默认，`rolldown-vite` 的过渡使命基本完成（其作为迁移隔离层的用法见 [04 节](./04-企业升级实战-从Vite5渐进升级.md)）。

## 七、本节小结

- Vite 5→8 的演进不是一条线，而是**两条独立主线**：A 架构抽象（Environment API，Vite 6 引入）、B 打包器替换（Rolldown，Vite 7 可选、Vite 8 默认）。记版本先定位这两条线的坐标。
- 主线 A 让「构建目标」从写死的 client/ssr 变成可扩展的「环境」，对纯 SPA 透明。
- 主线 B 用单一 Rust 打包器 Rolldown 统一 dev/build，消灭了双引擎时代的行为不一致，并带来 10–30x 构建提速（基准区间，非保证）。
- Vite 8 保留兼容层：`rollupVersion`/`esbuildVersion` 仍在，是兼容与兜底，不是主力。
- 用 `01-版本探针` demo 跑一行命令，看你本地真实的引擎版本，永远以实测为准。

## 八、可直接用于项目的 checklist

- [ ] 拿到一个项目，先看 `package.json` 的 vite 版本，再分别判断它在「架构线」和「打包器线」的位置。
- [ ] 用 `npm ls vite` / 本节探针确认**实际安装**版本，而不是只看 `^x` 范围。
- [ ] 判断是否需要关心 Environment API：纯 SPA 可忽略；有 SSR/边缘/多运行时需求才深入（见使用篇 [04 多环境章](../04-多环境与工程化场景/01-EnvironmentAPI落地多环境多运行时.md)）。
- [ ] 判断打包器现状：Vite 8 默认 Rolldown；Vite 7 默认仍是 esbuild+Rollup，可用 `rolldown-vite` 试水。
- [ ] 凡涉及「某版本变了什么」的结论，确认它标注了时间基线，避免把阶段性事实当永久结论。
