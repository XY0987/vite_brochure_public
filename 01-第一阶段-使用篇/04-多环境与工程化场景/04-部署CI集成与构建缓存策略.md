# 04 · 部署、CI 集成与构建缓存策略

> 本节解决的真实工程问题：本地 `vite build` 跑得好好的，一上线就翻车——部署到子路径 `https://x.com/my-app/` 后，页面全白、控制台一片 404；改了一行业务代码，用户却要重新下载整个几 MB 的 bundle，缓存形同虚设；CI 里构建忽快忽慢、偶尔因为 Node 版本不对直接挂掉；线上报个错，堆栈全是 `index-a3f9.js:1:28471` 这种压缩后的鬼画符根本没法定位。这些都属于「**代码写完之后、真正交付给用户之前**」的工程环节，是 demo 教程通常略过、却最影响线上稳定性的部分。本节把部署、CI 集成、构建缓存三件事一次讲清，给你一套从 `vite build` 到稳定上线的可落地配置。

事实基线：2026 年中，Vite 8.x（默认 Rolldown 打包器）。

---

## 一、部署第一坑：base 与部署路径

`vite build` 默认假设你的应用部署在**域名根**（`https://x.com/`），产物里资源都用绝对路径 `/assets/xxx.js` 引用。一旦你实际部署在**子路径**（`https://x.com/my-app/`），这些 `/assets/...` 就会去 `https://x.com/assets/...` 找文件——404、白屏。

解法是 `base`：告诉 Vite 资源引用的公共前缀。

```js
// vite.config.js
export default defineConfig({
  // 部署在 https://x.com/my-app/ → 设成 '/my-app/'
  base: '/my-app/',
});
```

或在命令行覆盖（CI 里按环境传更灵活）：

```bash
vite build --base=/my-app/
```

设对后，`dist/index.html` 里的引用会变成 `/my-app/assets/xxx.js`，线上就能正确找到。

> 几个 `base` 的常见取值：
>
> - 域名根部署 → `'/'`（默认，不用配）。
> - 子路径部署 → `'/my-app/'`（**前后都要带斜杠**）。
> - CDN 绝对地址 → `'https://cdn.x.com/assets/'`。
> - 完全相对路径（产物可放任意层级，如内嵌、Electron）→ `'./'`。

## 二、长效缓存：靠内容哈希 + 稳定分包

「改一行代码、用户却要重下整个 bundle」是缓存没做对。做对的目标是：**只有真正变了的文件才让用户重新下载，其余继续命中浏览器缓存。** Vite 默认已经帮你做了一半，另一半要你配。

### 默认这一半：内容哈希

Vite 构建产物文件名自带**内容哈希**：`index-BzET6dGB.js`。文件内容变了，哈希才变、文件名才变；内容没变，文件名不变，配合服务器 `Cache-Control: max-age=31536000, immutable`，用户就能长期缓存。这是长效缓存的前提。

### 要你配的另一半：把「稳定」与「易变」拆开

问题在于：如果所有代码打成一个大 chunk，哪怕你只改一个字，整个 chunk 的哈希都变，用户重下全部。所以要**把「很少变的」和「经常变的」拆成不同 chunk**——典型就是把第三方依赖（`node_modules`，很少变）单独拆成 vendor chunk，业务代码改动不影响它，vendor 缓存持续命中。

Vite 8（Rolldown）用 `output.codeSplitting` 配分包：

```js
// vite.config.js
export default defineConfig({
  build: {
    rolldownOptions: {
      output: {
        codeSplitting: {
          groups: [
            // 把第三方依赖拆成 vendor chunk
            { name: 'vendor', test: /node_modules/ },
          ],
        },
      },
    },
  },
});
```

> 命名演进（典型的版本漂移，照抄旧文章容易踩雷）：
>
> - `manualChunks`（函数式）：Vite 5–7 / Rollup 的写法，Vite 8 仍通过兼容层支持。
> - `advancedChunks`：Rolldown 早期引入的名字，**已 deprecated**，现在用会告警。
> - `codeSplitting`：当前的名字，配置结构（`{ groups: [...] }`）与 `advancedChunks` 一致。
> - `rollupOptions`：Vite 8 仍通过兼容层支持，但推荐迁移到 `rolldownOptions`。
>
> 这正是本小册反复强调的：版本演进里 API 名字会变，**以你安装版本的告警/文档为准**，别照搬过时博客。

另外，配合动态 `import()` 做路由级/功能级懒加载，能进一步把「首屏不需要的代码」拆成独立 chunk，按需下载：

```js
// 点击时才下载这个大功能的 chunk
button.addEventListener('click', async () => {
  const { runBigFeature } = await import('./big-feature.js');
  runBigFeature();
});
```

## 三、后端集成：manifest.json

如果你的前端产物不是独立部署，而是要**嵌进后端模板**（Rails、Laravel、Django、自研 SSR），后端怎么知道 `main.js` 这次构建出来的带哈希文件名是 `index-BzET6dGB.js`？答案是构建清单 `manifest.json`：

```js
build: {
  manifest: true,   // 生成 dist/.vite/manifest.json
}
```

它记录「源文件 → 带哈希产物」的映射及依赖关系：

```json
{
  "index.html": {
    "file": "assets/index-BzET6dGB.js",
    "isEntry": true,
    "imports": ["_vendor-DxM5qy1i.js"],
    "dynamicImports": ["src/big-feature.js"]
  }
}
```

后端读这个 JSON，就能在模板里注入正确的带哈希文件名、并根据 `imports` 预加载依赖 chunk。

## 四、线上报错定位：sourcemap

产物是压缩的，线上报错堆栈是 `index-a3f9.js:1:28471` 这种没法看的东西。开启 sourcemap 才能映射回源码位置：

```js
build: {
  sourcemap: true,   // 产出 .js.map
}
```

> 安全提醒：**别把** `.map` **文件公开暴露给公网用户**（等于把源码送人）。标准做法是：构建产出 sourcemap → 上传到 Sentry 等错误监控平台 → 从公开部署目录删掉 `.map`，或用 `hidden` 模式（生成 map 但不在 js 里写引用注释）。

## 五、CI 集成：三个必须做对的点

CI 里跑 Vite 构建，有三件事最容易翻车：

### 1. 锁定 Node 版本

Vite 8 硬性要求 **Node ≥ 20.19 或 ≥ 22.12**。CI 镜像默认 Node 版本不对，会直接安装失败或运行异常。

```yaml
- uses: actions/setup-node@v4
  with:
    node-version: '22'
    cache: 'npm'        # 自动缓存依赖，加速安装
```

### 2. 用 `npm ci` 而非 `npm install`

CI 里用 `npm ci`（pnpm 用 `pnpm i --frozen-lockfile`、yarn 用 `yarn --immutable`）：严格按 lock 文件安装，**可复现、更快**，且 lock 与 `package.json` 不一致时直接报错（暴露问题而非悄悄改 lock）。

### 3. 类型检查要单独卡——Vite 不做类型检查

这是最容易被忽略的一点：**Vite（用 esbuild/Oxc）只做 TS 转译，不做类型检查**（详见 [01 核心使用 / TypeScript 处理](../01-核心使用/07-TypeScript处理.md)）。也就是说，类型错误**不会让** `vite build` **失败**。要在 CI 单独加一道类型卡点：

```yaml
- run: npx tsc --noEmit        # 或 vue-tsc --noEmit
- run: npm run build
```

完整的最小 CI 工作流（配套 demo 里有 `ci.example.yml`；因 demo 是纯 JS、无 `tsconfig`，其中 `tsc --noEmit` 一步已注释，TS 项目取消注释即可）：

```yaml
name: ci
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22', cache: 'npm' }
      - run: npm ci
      - run: npx tsc --noEmit      # 类型检查单独卡（Vite 不做）
      - run: npm run build
      - uses: actions/upload-artifact@v4
        with: { name: dist, path: dist }
```

## 六、构建缓存策略：让重复构建更快

- **依赖安装缓存**：CI 里 `actions/setup-node` 的 `cache: 'npm'` 按 lock 文件哈希缓存 `~/.npm`，命中后省掉重复下载——这是性价比最高的一项。
- **Vite 依赖预构建缓存**：Vite 的依赖预构建结果缓存在 `node_modules/.vite`，本地反复启动 dev 会复用。CI 里若每次全新安装则意义不大，但**自托管 runner / 复用工作目录**时可缓存它加速 dev 类任务。
- **Vite 8 / Rolldown 的模块级持久缓存**：Vite 8 单打包器架构解锁了更强的持久化缓存能力（构建产物按模块缓存、增量重建），这是相比 Vite 5–7 双引擎时代的实质进步——具体随版本演进，以当前文档为准。
- **别缓存错东西**：`dist/` 是构建产物，不要跨提交缓存它（会拿到旧产物）；该缓存的是「输入」（依赖），不是「输出」（产物）。

## 七、动手：一份覆盖部署+缓存的构建配置

配套 demo 把 `base`、`codeSplitting`、`manifest`、`sourcemap`、动态 import 全放进一个最小项目，外加一份可直接用的 CI 工作流。

配套代码：[第一阶段-使用篇/04-多环境与工程化场景/04-部署与构建缓存/](https://github.com/XY0987/vite_brochure_code_public/tree/main/第一阶段-使用篇/04-多环境与工程化场景/04-部署与构建缓存/)

```bash
cd vite_brochure_code_public/第一阶段-使用篇/04-多环境与工程化场景/04-部署与构建缓存
npm install
npm run build           # 默认 base='/'
npm run build:subpath   # base='/my-app/'，对比资源前缀变化
```

观察点：

1. `dist/assets/` 里有 `index-*`、`vendor-*`（被 `codeSplitting` 拆出）、`big-feature-*`（动态 import 拆出）三个带**内容哈希**的 chunk。
2. 只改 `src/main.js`、不动 `vendor-like.js`，重新 build——`vendor-*` 哈希**不变**（缓存命中），只有 `index-`* 变。这就是「稳定/易变拆开」的收益。
3. `npm run build:subpath` 后看 `dist/index.html`，资源前缀变成 `/my-app/`——子路径部署的关键。
4. 看 `dist/.vite/manifest.json` 的源名→产物映射与 `imports`/`dynamicImports`。
5. `dist/assets/*.js.map` 是 sourcemap；`ci.example.yml` 是可直接落地的 CI 工作流。

## 八、本节小结

- 部署第一坑是 `base`：子路径部署必须设 `base: '/子路径/'`，否则资源 404 白屏。
- 长效缓存 = 内容哈希（默认有）+ 稳定分包（`output.codeSplitting` 把 `node_modules` 拆 vendor）+ 动态 import 懒加载。
- 分包 API 名字随版本漂移：`manualChunks`（旧）→ `advancedChunks`（deprecated）→ `codeSplitting`（当前），以安装版本为准。
- 后端集成用 `build.manifest` 生成清单；线上定位用 `build.sourcemap`，但别公开暴露 `.map`。
- CI 三要点：锁 Node 版本（20.19+/22.12+）、用 `npm ci`、**类型检查单独卡**（Vite 只转译不检查）。
- 缓存该缓存「输入」（依赖）不是「输出」（产物）；`actions/setup-node` 的 `cache: 'npm'` 性价比最高。

## 九、可直接用于项目的 checklist

- [ ] 确认部署路径，子路径部署设 `base`（前后带斜杠），或 CI 里 `--base=` 传入。
- [ ] 用 `output.codeSplitting`（旧项目 `manualChunks`）把 `node_modules` 拆成 vendor，分离稳定与易变代码。
- [ ] 首屏不必需的功能/路由用动态 `import()` 懒加载。
- [ ] 需要后端集成时开 `build.manifest`；按 manifest 注入带哈希文件名。
- [ ] 开 `build.sourcemap` 做线上定位，但不要把 `.map` 公开部署，上传到错误监控平台。
- [ ] CI 锁 Node 版本满足 Vite 8、用 `npm ci`、把 `tsc --noEmit` 作为独立步骤卡类型。
- [ ] CI 缓存依赖（`cache: 'npm'`），不要缓存 `dist/` 构建产物。
