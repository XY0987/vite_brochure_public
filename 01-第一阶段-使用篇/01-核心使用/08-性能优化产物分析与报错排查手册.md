# 08 · 性能优化、产物分析与常见报错排查手册

> 本节解决的真实工程问题：dev 启动越来越慢、构建几分钟、打出来的包好几兆首屏白屏、终端飘红一堆看不懂的报错。本节给你一套**系统方法**：怎么量化、怎么定位、怎么对症下药，而不是网上抄一段配置碰运气。最后附一份高频报错速查手册。

事实基线：2026 年中，Vite 8.x（Rolldown 单引擎，分包推荐用 `codeSplitting`；`advancedChunks` 是早期 Rolldown 过渡名，已 deprecated；构建较 Rollup 时代快 10–30×）。

> 本节的报错部分是“速查入口”：先帮你按现象快速定位方向。CJS/ESM 混用、依赖预构建失败、HMR 退化、资源路径、sourcemap 等真实工程里的复杂链路，详见下一节 [09 真实工程排障专题](./09-真实工程排障专题.md)。

---

## 一、先分清你在优化哪个阶段

“Vite 慢”是个含糊的说法。先定位是哪一段慢，三段的优化手段完全不同：

| 阶段 | 症状 | 主要手段 |
|---|---|---|
| dev 启动 | `npm run dev` 到能访问要等很久 | 预构建、`server.warmup`、减少入口扫描 |
| dev 运行 | 改代码后 HMR 慢、页面卡 | 检查 HMR 是否退化为全量、减少超大模块 |
| build 构建 | `npm run build` 耗时长 | 升级到 Vite 8（Rolldown）、分包、关掉不必要的 sourcemap |
| 产物体积 | 包太大、首屏慢 | 分包、按需加载、tree-shaking、external CDN |

## 二、dev 性能

### 1. 预构建（最大头）

dev 启动慢的头号原因往往是依赖预构建。看 [05 依赖预构建](./05-依赖预构建.md)：用 `optimizeDeps.include` 提前纳入路由级依赖，避免运行中途的“卡顿+刷新”。

### 2. `server.warmup`：提前编译热点模块

dev 是按需编译，首次访问某个大模块会现编译。可以让 Vite 启动后**预热**这些高频模块：

```ts
export default defineConfig({
  server: {
    warmup: {
      clientFiles: ['./src/main.ts', './src/views/Home.vue'],
    },
  },
});
```

### 3. 避免 barrel 文件拖累

`index.ts` 里 `export * from './everything'` 这种 barrel 文件会让一个小 import 牵连出一大片模块编译，dev 变慢。按需直接 import 具体文件。

## 三、build 性能与产物体积

### 1. 升级 Vite 8（Rolldown）是最大的一次性提速

Vite 8 用 Rust 的 Rolldown 统一 dev/build，构建较 Rollup 时代快约 10–30×。如果项目还在 Vite 5/6 且构建慢，**升级本身就是最有效的优化**（迁移注意事项见后续「版本差异」章节）。

### 2. 分包：`manualChunks` → `codeSplitting`

分包的目的：把不常变的第三方依赖单独成 chunk，配合内容哈希实现**长效缓存**——你发版改业务代码，用户的 `vendor` chunk 缓存仍命中，不用重下。

Vite 8 推荐用 Rolldown 的 `codeSplitting`（旧的 `manualChunks` 有兼容层但建议迁移；早期 Rolldown 的 `advancedChunks` 已 deprecated，命名演进详见 [05 章配置迁移](../05-版本差异与升级迁移/02-各版本升级要点与配置迁移.md#迁移点-2outputmanualchunks--outputcodesplitting注意中间还有个-advancedchunks)）：

```ts
// Vite 8（Rolldown）写法
export default defineConfig({
  build: {
    rolldownOptions: {
      output: {
        codeSplitting: {
          groups: [
            // 按 node_modules 里的第三方包名分组：稳定依赖单独缓存
            { name: 'react-vendor', test: /node_modules\/(react|react-dom)\// },
            { name: 'lodash', test: /node_modules\/lodash/ },
            // 按业务目录分组：适合后台管理、图表模块这类相对独立的大块业务代码
            { name: 'admin', test: /src\/admin\// },
            { name: 'charts', test: /src\/charts\// },
          ],
        },
      },
    },
  },
});
```

不要一上来写 `{ name: 'vendor', test: /node_modules/ }`，再在后面写更细的 `lodash` / `react` 分组。前者会匹配几乎所有第三方依赖，容易把后面的细分规则吞掉，或者让优先级变得不直观。实际项目里更推荐按“稳定且体积较大的依赖”明确分组，剩余依赖交给默认分包策略。

旧版（Vite 5–7 / Rollup）对照：

```ts
build: {
  rollupOptions: {
    output: {
      manualChunks(id) {
        // 旧版按第三方包名分组
        if (id.includes('node_modules/vue') || id.includes('node_modules/vue-router')) {
          return 'vendor';
        }
        // 旧版按业务目录分组
        if (id.includes('/src/admin/')) return 'admin';
        if (id.includes('/src/charts/')) return 'charts';
      },
    },
  },
}
```

> 迁移要点：`rollupOptions` → `rolldownOptions`、`manualChunks` → `codeSplitting`。Vite 8 提供兼容层会自动转换大部分写法，但对依赖 Rollup 内部行为的复杂 `manualChunks` 函数可能失效，需手动改写。

业务代码不是按第三方包名来划分。最常见做法是用路由级或组件级动态 `import()`，让 Vite 自动把它们拆成按需加载的 chunk；如果确实有稳定的大块业务模块，也可以像上面那样按目录规则分组，但要先用产物分析确认它值得单独拆。

### 3. 按需加载（code splitting）

路由/重组件用动态 `import()`，Vite 自动拆成独立 chunk，按需下载：

```js
const Chart = () => import('./HeavyChart.js'); // 只有用到时才下载这个 chunk
```

### 4. external + CDN（可选）

把超大依赖（如某些可视化库）标成 external，运行时从 CDN 加载，减小自身产物。代价是多一个外部依赖点，按需权衡。

## 四、产物分析：先量化再优化

不要凭感觉优化。先看清“到底哪个 chunk 大、为什么大”。

### 1. 看构建输出

`vite build` 结束会打印每个 chunk 的大小和 gzip 后大小。超过阈值（默认 500KB）会黄字警告 `Some chunks are larger than 500 kB`。这是第一手信息。

### 2. 可视化分析：`rollup-plugin-visualizer`

```bash
npm install -D rollup-plugin-visualizer
```

```ts
import { visualizer } from 'rollup-plugin-visualizer';

export default defineConfig({
  plugins: [
    visualizer({ open: true, gzipSize: true, filename: 'dist/stats.html' }),
  ],
});
```

`vite build` 后会生成 `dist/stats.html`，一张 treemap 直观显示**每个依赖占了多少体积**——这是定位“谁把包撑大了”的最有效工具。常见发现：moment 全量 locale、lodash 全量引入、重复打包的依赖。

### 3. 控制警告阈值

确认大 chunk 合理（如刻意的 vendor）时，调高阈值消除噪音：

```ts
build: { chunkSizeWarningLimit: 1000 }
```

## 五、常见报错排查手册

按“看到什么 → 大概率原因 → 怎么办”组织。更深入的工程排障见 [09 专题](./09-真实工程排障专题.md)。

### 1. `Failed to resolve import "xxx"`
- 原因：路径/别名错、依赖没装、预构建缓存过期。
- 办法：核对路径与别名（[04](./04-静态资源CSS别名与路径解析.md)）；`npm i` 确认依赖在；`vite --force` 重建预构建。

### 2. `[vite] Internal server error: ... is not exported by ...`
- 原因：CJS/ESM 互操作问题，import 写法和包实际导出不匹配。
- 办法：换 `import pkg from 'x'` 或 `import * as pkg`；`optimizeDeps.include` 该包。详见 [09](./09-真实工程排障专题.md)。

### 3. 构建成功但线上白屏、资源 404
- 原因：`base` 没配成子路径（[02](./02-项目搭建与vite.config配置详解.md)）。
- 办法：部署在 `/sub/` 就把 `base` 设成 `/sub/`，重新 build。

### 4. `Some chunks are larger than 500 kB`
- 原因：大依赖没分包/没按需加载。
- 办法：上 visualizer 定位，分包 + 动态 import（本节三、四）。

### 5. dev 正常、build 报错（或反之）
- 原因：dev/build 双路径差异（[01](./01-Vite定位与诞生背景.md)）。
- 办法：以 build 为准排查；注意只在 dev 生效的配置（如 `server.proxy`）。

### 6. `The CJS build of Vite's Node API is deprecated` 之类弃用警告
- 原因：用了旧的导入/API 形态。
- 办法：按版本迁移指南更新（配置文件用 ESM、`import.meta.url` 等）。

### 7. HMR 不生效 / 退化为整页刷新
- 原因：模块不可热替换、循环依赖、改了被很多模块依赖的文件。
- 办法：见 [09 HMR 专题](./09-真实工程排障专题.md)。

## 七、本节小结

- 优化前先定位阶段：dev 启动 / dev 运行 / build / 产物体积，手段各不同。
- dev：预构建 + `server.warmup` + 避免 barrel；build：升级 Vite 8、分包、动态 import。
- 分包用 `codeSplitting`（Vite 8）实现 vendor 长效缓存；`rollupOptions/manualChunks` 是旧写法，`advancedChunks` 只是已废弃的过渡名。
- 优化必须先量化：看构建输出 + `rollup-plugin-visualizer` 的 treemap，别凭感觉。
- 报错排查手册按“现象→原因→办法”查，复杂的进 [09 专题](./09-真实工程排障专题.md)。

## 八、可直接用于项目的 checklist

- [ ] 明确当前要优化的是哪一阶段（启动/运行/构建/体积），别一锅炖。
- [ ] 构建慢且版本低时，先评估升级 Vite 8（Rolldown）的收益。
- [ ] 第三方依赖用 `codeSplitting.groups` 分到 `vendor`，配合哈希做长效缓存。
- [ ] 大组件/路由用动态 `import()` 按需加载。
- [ ] 接入 `rollup-plugin-visualizer`，每次发版前看一眼体积大头。
- [ ] 大 chunk 警告先用 visualizer 定位根因，再决定优化或调高阈值。
- [ ] 收藏报错速查手册；遇到 dev/build 不一致，一律以 build 为准排查。
