# 05 · 依赖预构建（dependency pre-bundling）：现象、配置、常见问题

> 本节解决的真实工程问题：为什么首次 `npm run dev` 会卡几秒、终端打印 “optimizing dependencies”？为什么有时浏览器疯狂请求几百个文件、页面卡死？为什么改了某个依赖的源码（比如调试 `node_modules` 里的包）却不生效？这些都指向同一个机制——**依赖预构建**。理解它，是排查启动慢和“依赖相关怪现象”的钥匙。

事实基线：2026 年中，Vite 8.x（预构建由 Rolldown/Oxc 工具链承担；行为与 esbuild 时代一致，速度更快）。

---

## 一、为什么需要预构建：两个非它不可的理由

Vite dev 期不打包业务代码，但**对 `node_modules` 里的第三方依赖是个例外——它要预先打包**。原因有二：

### 理由 1：CommonJS / UMD → ESM 的转换

浏览器原生 ESM 只认 `import`/`export`。但海量 npm 包仍是 CommonJS（`module.exports`）或 UMD 格式，浏览器**没法直接 `import`**。预构建把这些依赖转换成标准 ESM，dev server 才能把它们当模块喂给浏览器。

### 理由 2：把“几百个小模块”合并成“一个请求”

很多包内部由大量小文件组成。最经典的是 `lodash-es`：你只 `import { debounce } from 'lodash-es'`，但它内部有 600+ 个互相 import 的模块。如果不预构建，浏览器会**瀑布式发起几百个请求**，dev 体验直接崩。

预构建把每个依赖**打成一个（或少数几个）ESM 文件**，于是 `import { debounce } from 'lodash-es'` 只产生一个网络请求。这就是为什么有时你会看到“没预构建时浏览器疯狂请求几百个文件”——那正是预构建没生效的症状。

> 一句话：预构建 = **格式归一（CJS→ESM）+ 请求合并（多文件→单文件）**。

## 二、现象：你会在哪看到它

1. **首次启动**：终端出现 `Pre-bundling dependencies` / `optimizing dependencies`，短暂等待。这是一次性成本，结果会被缓存。
2. **缓存目录**：产物在 `node_modules/.vite/deps/`。下次启动若依赖没变，直接用缓存、秒起。
3. **新依赖触发**：装了新包并 import 后，Vite 检测到缓存里没有，会触发**二次预构建**并自动刷新页面（终端提示 `new dependencies optimized`）。
4. **请求形态**：浏览器里第三方依赖的请求路径形如 `/node_modules/.vite/deps/lodash-es.js?v=xxxxxx`，带一个版本 query 用于缓存失效。

## 三、缓存机制：什么时候会重新预构建

Vite 通过一个哈希判断缓存是否有效。**以下任一变化都会让缓存失效、触发重新预构建**：

- `package.json` 的 `dependencies` 变化；
- 锁文件（`package-lock.json` / `pnpm-lock.yaml` / `yarn.lock`）变化；
- `vite.config` 里影响预构建的字段（如 `optimizeDeps`、`resolve.alias`）变化。

手动强制重建：

```bash
vite --force          # 忽略缓存，强制重新预构建
# 或直接删缓存
rm -rf node_modules/.vite
```

> 这正是“改了 `node_modules` 里某个包源码不生效”的原因：那个包已被预构建并缓存，你的改动没进缓存。调试依赖时要么 `--force`，要么把它从预构建里排除（见下文 `exclude`）。

## 四、配置：`optimizeDeps` 五个最常用项

```ts
export default defineConfig({
  optimizeDeps: {
    // 1. 强制把某些依赖纳入预构建（解决“没被自动发现”的依赖）
    include: ['lodash-es', 'some-cjs-pkg'],

    // 2. 排除某些依赖不预构建（调试该依赖源码、或它本身是合法 ESM 不需要处理）
    exclude: ['my-local-esm-lib'],

    // 3. 给底层打包器传选项（如把某些扩展名当 jsx 处理）
    //    Vite 8 推荐用 rolldownOptions；esbuildOptions 已 deprecated（会自动转换成 rolldownOptions），仅为兼容保留
    rolldownOptions: {
      // 预构建阶段透传给 Rolldown 的选项
    },

    // 4. 强制每次启动都重新预构建（一般不用，调试时偶尔用）
    force: false,
  },
});
```

### 什么时候用 `include`

Vite 启动时通过扫描入口来发现依赖，但有些依赖是**运行时动态 import、或藏在被 `exclude` 的包里、或只在某些路由才加载**，首次扫描发现不了。表现为：访问到某个页面时突然卡一下、终端打印“new dependencies optimized”、页面刷新。把这类依赖写进 `include` 可以让它在启动时就被预构建，避免运行中途的“卡顿 + 刷新”。

### 什么时候用 `exclude`

- 你要**调试某个依赖的源码**（排除后 Vite 直接用其原始文件，改动即时生效）。
- 某个包本身是规范的 ESM、且不希望被预构建改写（少数场景）。
- 某个包预构建会出错（兼容性问题），临时排除绕过。

## 五、常见问题与排查

### 问题 1：启动后浏览器发起几百个请求、巨慢

**原因**：某依赖没被预构建（可能被错误 `exclude`，或它是 CJS 但没识别到）。
**排查**：看 Network 里是不是某个包的内部小文件被一个个请求；检查 `optimizeDeps.exclude` 是否误排除；尝试把它加进 `include`。

### 问题 2：装了新包后报错 “Failed to resolve import” 或白屏

**原因**：预构建缓存过期 / 没触发重建。
**解决**：`vite --force` 或删 `node_modules/.vite` 重启。

### 问题 3：改 `node_modules` 里依赖源码不生效

**原因**：被预构建并缓存了（见第三节）。
**解决**：`optimizeDeps.exclude` 该包，或 `--force`。

### 问题 4：CJS 包按 ESM 方式 import 拿不到具名导出 / default 不对

**原因**：CJS→ESM 互操作的经典坑（`module.exports` 与 `export default` 的映射）。
**解决**：预构建通常能处理；仍出问题时，确认导入写法（`import pkg from 'x'` vs `import { y } from 'x'`），必要时 `optimizeDeps.include` 显式纳入。这类 CJS/ESM 混用问题在 [09 工程排障专题](./09-真实工程排障专题.md) 有系统讲解。

### 问题 5：monorepo 里 workspace 内部包没被预构建 / 频繁触发

workspace 软链的内部包默认行为与普通依赖不同，相关细节属于第一阶段后续「monorepo」章节，这里先知道：dev 侧主要用 `optimizeDeps.include/exclude` 和 `server.fs.allow` 处理；SSR 构建侧常配合 `ssr.noExternal`。旧文章里常见的 `build.commonjsOptions` 在 Vite 8 已是 no-op 兼容项，不要再把它当成解决预构建或 CJS 互操作问题的入口。

## 六、动手：观察预构建

配套代码：[第一阶段-使用篇/01-核心使用/05-依赖预构建/](https://github.com/XY0987/vite_brochure_code_public/tree/main/第一阶段-使用篇/01-核心使用/05-依赖预构建/)

demo 依赖 `lodash-es`（典型多模块包），让你直观看到预构建前后的网络请求差异。

```bash
cd vite_brochure_code_public/第一阶段-使用篇/01-核心使用/05-依赖预构建
npm install
npm run dev
```

观察点：
1. 首次启动终端打印预构建信息；`ls node_modules/.vite/deps` 能看到产物。
2. 浏览器 Network 里 `lodash-es` 是**一个** `deps/lodash-es.js?v=...` 请求，而不是几百个。
3. 实验对比：把 `vite.config.ts` 里 `optimizeDeps.exclude: ['lodash-es']` 取消注释，`npm run dev` 重启，再看 Network——这次会变成大量 `lodash-es` 内部小文件请求（亲眼见证预构建的价值）。
4. 跑 `npm run dev -- --force` 看强制重建。

## 七、本节小结

- 预构建做两件事：**CJS/UMD → ESM 的格式归一** 和 **多文件 → 单文件的请求合并**，是 dev 体验流畅的前提。
- 产物缓存在 `node_modules/.vite/deps/`，由 `package.json`/锁文件/相关配置的哈希决定是否失效。
- `optimizeDeps.include`（补发现不到的依赖）、`exclude`（调试依赖源码 / 绕过问题）是两个核心开关。
- “启动慢/几百请求”“新依赖报错”“改依赖不生效”都能用预构建机制解释和解决。

## 八、可直接用于项目的 checklist

- [ ] 遇到“访问某页面时卡顿 + 自动刷新”，把该页用到的依赖加进 `optimizeDeps.include`。
- [ ] 需要调试 `node_modules` 里某依赖源码时，用 `exclude` 或 `--force`。
- [ ] 装/删依赖后若出现解析报错，先 `vite --force` 或删 `node_modules/.vite` 再排查。
- [ ] 浏览器出现某个包的大量内部小请求时，检查是否被误 `exclude`、是否需要 `include`。
- [ ] CI / 容器构建里清楚预构建缓存不可跨依赖变更复用（锁文件变了会重建）。
