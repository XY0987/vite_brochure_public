# 01 · Vite 的定位与诞生背景：它解决了 webpack 时代的什么痛点

> 本节解决的真实工程问题：团队里 webpack 项目启动要等一两分钟、改一行代码热更新转圈好几秒，有人提议换 Vite。换之前你得先回答一个问题——**Vite 到底快在哪？是“换了个更快的打包器”，还是根本换了一套思路？** 想不清楚这点，迁移时就会掉进“为什么 dev 正常、build 出错”之类的坑。

事实基线：2026 年中，Vite 8.x，Rolldown 成为默认唯一打包器。

---

## 一、一句话定位

Vite 是一个**面向现代浏览器原生 ES Module 的前端构建工具**，它把开发期和生产期当成两个不同的问题来解决：

- **开发期**：利用浏览器原生支持 ESM 的能力，**不打包**，按浏览器的请求“按需编译”单个模块。
- **生产期**：用打包器（Vite 2–7 是 Rollup，Vite 8 起是 Rolldown）做**完整打包**，产出优化过的静态资源。

记住这条主线——**“dev 不打包、build 打包”**——本小册后面几乎所有现象（启动快、HMR 快、偶发 dev/build 行为不一致）都能从这里推出来。

## 二、回到 webpack 时代：痛点到底是什么

webpack 是“打包器（bundler）”范式的代表。它的核心心智是：**在你能看到页面之前，先把整棵依赖图打成一个（或几个）bundle。**

这套范式在 ESM 还没普及的年代是必需的——浏览器不认识 `import`，模块化只能靠工具在构建时模拟。但随着项目变大，它带来三个结构性痛点：

### 痛点 1：冷启动随项目规模线性变慢

`webpack serve` 启动时要先**爬完整棵依赖图、把所有模块打包**，才能给你第一个可访问的页面。模块越多，启动越慢——大型项目冷启动几十秒到几分钟是常态。这不是某个配置没调好，而是“先打包再服务”范式的必然代价。

### 痛点 2：HMR 速度也随规模下降

改一行代码，webpack 需要重新构建受影响的 bundle 区块。bundle 越大、依赖关系越复杂，重建和推送的成本越高，热更新从“秒级”退化到“好几秒”。

### 痛点 3：配置复杂度高

loader 链、`resolve`、`optimization.splitChunks`、各种 plugin……为了把“不同类型资源都塞进打包流程”，webpack 暴露了大量需要手工拼装的配置。能跑起来不难，但**讲清每一项为什么这么配**很难——这恰恰是 AI 也替代不了的工程判断。

> 这里不是说 webpack 不好。它在“需要极致打包控制、生态插件最全、兼容老项目”的场景仍然有价值（见本章第 6 节横向对比预告）。痛点是**范式**带来的，不是实现不够努力。

## 三、Vite 的破局点：开发期不打包

2020 年 ESM 已被现代浏览器广泛支持。尤雨溪（Vue 作者）抓住的关键洞察是：**既然浏览器自己就认识 `import`，开发期为什么还要我们替它打包？**

于是 Vite 在开发期这样工作：

1. 启动一个 dev server，**几乎瞬间就绪**（不需要先打包整棵依赖图）。
2. 浏览器加载 `index.html`，遇到 `<script type="module" src="/src/main.js">`，发起请求。
3. dev server 收到对 `/src/main.js` 的请求，**只编译这一个模块**（比如把 `.vue`/`.ts`/`.jsx` 转成浏览器能跑的 JS），返回。
4. 浏览器解析返回内容，发现里面又 `import './foo.js'`，**再发一个请求**，server 再按需编译 `foo.js`……

也就是说，**编译工作量从“项目总规模”变成了“当前页面真正用到的模块”**。这就是冷启动与规模解耦、几乎恒定快的根本原因。

配套这套机制还有两个关键设计（后续章节展开）：

- **依赖预构建**：`node_modules` 里的第三方依赖用 esbuild（Vite 8 起是 Oxc/Rolldown 工具链）预先打成 ESM 并缓存，避免成百上千个小请求拖慢浏览器。详见 [05 依赖预构建](./05-依赖预构建.md)。
- **精准 HMR**：基于模块图（module graph），文件变更时只让**受影响的模块**失效并热替换，速度与项目总规模基本无关。

## 四、那为什么生产环境还要打包

既然 dev 不打包这么爽，build 为什么不一样照搬？因为生产环境的约束完全不同：

- 浏览器对**大量小文件的网络请求**有开销（HTTP/2 缓解但没消除），未打包会产生瀑布式请求。
- 需要 **tree-shaking、压缩、代码分割、长效缓存哈希**等一系列产物优化，这些是打包器的强项。
- 还要考虑**目标浏览器兼容性**：生产环境的用户设备更复杂，不一定都能直接运行现代语法或原生 ESM，需要 build 阶段做必要处理。

所以 Vite 生产期交给打包器做完整打包。这里就埋下了一个本小册反复强调的事实：**dev 与 build 走的是两条不同的代码路径**，因此偶尔会出现“dev 正常、build 异常”或反之的问题——理解了“双路径”，这类 bug 就不再神秘。

## 五、版本演进：双引擎 → 单引擎（选型必须知道的事实）

这是 Vite 区别于其他小册、也是企业选型最关心的主线：

| 版本 | 时间 | dev 引擎 | build 引擎 | 关键变化 |
|---|---|---|---|---|
| Vite 2–5 | 2021–2023 | esbuild | Rollup | **双引擎**：dev 用 esbuild 快，build 用 Rollup 产物优 |
| Vite 6 | 2024.11 | esbuild | Rollup | 引入 Environment API（多环境模型），架构重构但兼容 |
| Vite 7 | 2025.06 | esbuild | Rollup（`rolldown-vite` 可选） | 清理废弃特性，Rolldown 以 drop-in 形式提供 |
| Vite 8 | 2026.03 | Rolldown | Rolldown | **单引擎**：Rolldown（Rust）统一 dev + build，Oxc 接管转译/压缩 |

“双引擎”时代有个长期被诟病的问题：dev（esbuild）和 build（Rollup）行为不完全一致，偶尔出现“开发好好的、上线挂了”。**Vite 8 用 Rolldown 统一 dev/build，正是为了从根上消除这种不一致**，同时把构建速度提升约 10–30×。这条“为什么从双引擎走向单引擎”的决策线，第二阶段讲实现、第三阶段讲设计动因。

这里不要误解成“build 完全不用 esbuild”。在 Vite 2–7 里，esbuild 仍可能参与 TS/JSX 转译、依赖预构建或压缩；真正的差异是：dev 阶段按浏览器请求做必要转译，依赖图随请求逐步建立；build 阶段由 Rollup 从入口开始完整构建依赖图并生成最终产物。

> 选型提示：企业现役大量项目仍在 Vite 5/6。是否升级到 8，要权衡 Rolldown 对依赖 Rollup 内部实现的插件的兼容性——这部分见第一阶段 [05 版本差异与升级迁移](../05-版本差异与升级迁移/README.md)（尤其 [企业升级实战](../05-版本差异与升级迁移/04-企业升级实战-从Vite5渐进升级.md)）。

## 六、动手感受：按需编译 vs 一次性打包

配套代码：[第一阶段-使用篇/01-核心使用/01-vite定位与诞生背景/](https://github.com/XY0987/vite_brochure_code_public/tree/main/第一阶段-使用篇/01-核心使用/01-vite定位与诞生背景/)

这个 demo 用一个故意拆成很多小模块的页面，让你在浏览器 Network 面板**亲眼看到** Vite dev server 是“一个模块一个请求、按需返回”的：

```bash
cd vite_brochure_code_public/第一阶段-使用篇/01-核心使用/01-vite定位与诞生背景
npm install
npm run dev
```

打开浏览器开发者工具的 Network 面板，按 JS 过滤，刷新页面，你会观察到：

1. 先请求 `index.html`，再请求 `/src/main.js`。
2. `main.js` 返回后，浏览器**逐个**请求它 import 的 `modules/*.js`——每个模块都是一条独立请求，源码原样可读（带 Vite 处理过的路径重写）。
3. 注释掉 `main.js` 里对某个模块的 import 再刷新，那个模块的请求就消失了——**没用到就不编译、不传输**，这正是“按需”。

再跑一次生产构建对比：

```bash
npm run build
npm run preview
```

这次 Network 里那一堆 `modules/*.js` 不见了，全被打进了少数几个带哈希的 chunk——这就是“dev 不打包、build 打包”的直观证据。

## 七、本节小结

- Vite 不是“更快的 webpack”，而是**换了范式**：开发期用浏览器原生 ESM 做按需编译，生产期才打包。
- 它解决 webpack 三大痛点：冷启动随规模变慢、HMR 变慢、配置复杂——前两个是范式收益，第三个是设计取舍。
- 代价是 **dev/build 双路径**可能行为不一致；Vite 8 用 Rolldown 统一引擎正是为了消除这个代价。
- 选型时，“dev 引擎 / build 引擎 / 是否单引擎”是必须先问清的事实。

## 八、可直接用于项目的 checklist

迁移评估 / 给团队讲清「为什么用 Vite」时，逐条确认：

- [ ] 能用一句话说清「dev 不打包、build 打包」，并据此解释启动为什么快。
- [ ] 知道当前项目目标 Vite 大版本（5/6/7/8）对应的 dev/build 引擎是什么。
- [ ] 升级到 Vite 8 前，已列出项目里依赖 Rollup 内部实现的插件清单（兼容性风险点）。
- [ ] 团队达成共识：dev 正常不代表 build 正常，上线前必须跑一次 `build` + `preview` 验证。
- [ ] 评估过项目对“大量小请求”的敏感度（极大型项目首屏 dev 体验，可结合预构建/`warmup` 优化，见 [08 性能优化](./08-性能优化产物分析与报错排查手册.md)）。
