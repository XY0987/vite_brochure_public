## 一、CJS / ESM 混用

### 症状
- `The requested module 'x' does not provide an export named 'default'`
- `'y' is not exported by ...`
- `import pkg from 'x'` 拿到的是个奇怪的 `{ default: ... }` 包裹对象
- `require is not defined` / `__dirname is not defined`（在浏览器或 ESM 上下文）

### 根因
ESM（`import`/`export`）和 CommonJS（`require`/`module.exports`）是两套模块系统，互操作有“阻抗失配”。Vite 全程拥抱 ESM；当依赖是 CJS、或你的代码混用两套语法时就会冲突。常见来源：
- 一个老 npm 包只提供 CJS，且 default/具名导出映射不符合预期。
- 配置文件（`vite.config`）被当 ESM 处理，却用了 `__dirname`/`require`。
- `package.json` 没有 `"type": "module"` 导致 `.js` 被当 CJS。

### 排查步骤
1. 确认报错的是哪个包、它的 `package.json` 的 `exports`/`main`/`module` 提供了什么格式。
2. 看自己的导入写法：默认导入 vs 具名导入 vs 命名空间导入。
3. 区分上下文：是浏览器代码、SSR(Node) 代码，还是配置文件。

### 解决
- 业务里导入 CJS 包：试 `import pkg from 'x'`（拿 default），或 `import * as pkg from 'x'`（命名空间），按包实际导出选。
- 把该包加进 `optimizeDeps.include`，让预构建把 CJS 转成规范 ESM（见 [05](./05-依赖预构建.md)）。
- 配置文件里别用 `__dirname`，用 `fileURLToPath(import.meta.url)`；别用 `require`，用 `import`。
- 自己项目统一 `"type": "module"`，避免 `.js` 歧义（需要 CJS 的脚本用 `.cjs`）。

## 二、依赖预构建失败

### 症状
- 启动时 `Failed to optimize dependencies` / 某依赖预构建报错。
- 装了新包后白屏、`Failed to resolve import`。
- 改了 `node_modules` 里依赖源码不生效。

### 根因
预构建缓存过期未重建、依赖本身格式有问题、或被错误 `include`/`exclude`。（机制见 [05](./05-依赖预构建.md)）

### 排查步骤
1. 删缓存重启：`rm -rf node_modules/.vite && npm run dev`，或 `vite --force`。
2. 仍失败：看报错指向哪个依赖，单独把它 `optimizeDeps.exclude` 试试能不能绕过。
3. 浏览器出现某包大量内部小请求 → 它没被预构建，`optimizeDeps.include` 它。

### 解决
- 缓存问题：`--force` / 删 `node_modules/.vite`。
- 调试依赖源码：`exclude` 该包（改动即时生效）。
- 发现不到的运行时依赖：`include` 该包。

## 三、HMR 退化为整页刷新

### 症状
- 改一个组件，整个页面刷新（而非局部热替换），状态丢失。
- 终端打印 `page reload` 而非 `hmr update`。

### 根因
HMR 基于模块图做精准更新。当一个模块**无法被热接受**时，Vite 沿依赖链向上找能接受更新的边界；如果一路找到入口都没有，就只能整页刷新。常见原因：
- 该模块/其依赖者没有声明 `import.meta.hot.accept`（框架插件通常自动处理组件 HMR，但你自己写的业务模块、工具模块不一定有热接受边界）。
- 改动了被极多模块依赖的“根”文件（如全局常量、被所有页面 import 的工具）。
- 存在循环依赖，破坏了热更新边界。
- 改了非 JS 的东西（如 `index.html`、部分配置）本就需要刷新。

### 排查步骤
1. 看终端是 `hmr update` 还是 `page reload`。
2. 看改的文件被多少模块依赖、有没有循环依赖。
3. 框架项目确认装了对应插件（`@vitejs/plugin-vue` / `@vitejs/plugin-react`），它们提供组件级 HMR/Fast Refresh。

### 解决
- 框架组件：确保用了官方插件，别把组件逻辑写在插件识别不了的地方。
- 普通模块要局部热更新：手动 `import.meta.hot.accept(cb)` 声明接受边界。
- 拆分“被所有人依赖”的大文件，缩小热更新影响面。
- 消除循环依赖。

## 四、资源路径错误

### 症状
- 线上 JS/CSS/图片 404，本地（dev/preview）正常。
- 部署到子目录后整站白屏。
- CSS 里 `url()` 指向的图片找不到。

### 根因
- `base` 没设成部署子路径（最常见，见 [02](./02-项目搭建与vite.config配置详解.md)）。
- 手写了源码绝对路径 `/src/assets/x.png` 而非让 Vite 解析（见 [04](./04-静态资源CSS别名与路径解析.md)）。
- 该用 `import` 拿哈希 URL 的资源，却放进了 `public/` 或写死了路径。

### 排查步骤
1. 看 404 资源的请求 URL：是不是少了部署前缀（→ `base` 问题）。
2. 看产物 `dist/index.html` 里资源路径前缀对不对。
3. 区分本地 preview 与线上：preview 默认 `base: '/'`，可能掩盖子路径问题。

### 解决
- 子路径部署：`base: '/sub/'`（或用相对 `base: './'`，注意它对 SSR/动态导入有限制）。
- 资源一律 `import` 让 Vite 解析，别手写源码绝对路径。
- 验证：`vite build` 后 `vite preview --base /sub/` 模拟子路径。

## 五、构建产物异常（dev 正常、build 出问题）

### 症状
- dev 一切正常，`build` 后某功能失效/报错/样式丢失。
- 生产环境出现 dev 没有的错误。

### 根因
**dev 与 build 是两条路径**（[01](./01-Vite定位与诞生背景.md)）：dev 按需编译不打包、不做 tree-shaking/压缩；build 完整打包并做这些优化。差异点常出在：
- tree-shaking 把“看似没用其实有副作用”的代码删了（缺 `sideEffects` 标记）。
- 仅 dev 生效的配置（`server.proxy`）被误当生产能力。
- 动态拼接的 import 路径 build 时无法静态分析。
- 环境变量在两种 mode 下取值不同。

### 排查步骤
1. 本地复现：`vite build && vite preview`，别用 dev 验证生产。
2. 开 sourcemap（见下节）定位到源码。
3. 二分法：怀疑 tree-shaking 时，逐步 `build` 缩小范围。

### 解决
- 有副作用的模块在其包 `package.json` 标 `"sideEffects"`，或避免被误删。
- 别依赖 `server.proxy` 当生产跨域方案。
- import 路径尽量静态可分析；动态部分用 `import.meta.glob`。
- 上线前流程固定：`build` + `preview` 自检（[03](./03-devserver构建预览与环境变量多模式.md)）。

## 六、sourcemap 与线上问题定位

### 症状
- 线上报错堆栈全是 `index-a1b2c3.js:1:23456`，压缩后根本看不出是哪行源码。

### 根因
生产产物默认不带 sourcemap（`build.sourcemap: false`），且被压缩，堆栈无法映射回源码。

### 解决
按需开 sourcemap，三种取值各有用途：

```ts
build: {
  sourcemap: true,       // 生成 .map 并在产物里用 //# sourceMappingURL 引用（会暴露源码）
  // sourcemap: 'hidden', // 生成 .map 但产物里不引用（上传给监控平台用，不暴露给用户）
  // sourcemap: 'inline',  // 内联进产物（体积大，一般不用于生产）
}
```

工程实践：
- **生产推荐 `'hidden'`**：构建出 `.map` 文件，**不**部署到公网，而是上传到 Sentry/监控平台，由平台把线上压缩堆栈还原成源码位置。既能定位又不泄露源码。
- 别把带 `//# sourceMappingURL` 的 `.map` 直接发到公网（等于公开源码）。
- dev 默认就有 sourcemap，无需配置。

### 排查步骤
1. 线上报错先看监控平台还原后的堆栈（前提是上传了 sourcemap）。
2. 没接监控：本地 `build` 开 `sourcemap: true` + `preview` 复现，用浏览器 devtools 映射回源码。

## 八、本节小结

六类高频故障的共同心法：

1. **CJS/ESM**：分清格式与上下文，用 `optimizeDeps.include` + 正确导入写法。
2. **预构建失败**：先 `--force`/删缓存，再用 `include`/`exclude` 对症。
3. **HMR 退化**：看 `hmr update` vs `page reload`，靠插件/`accept`/拆分根文件/解循环依赖。
4. **资源路径**：90% 是 `base` 没配；资源一律 import 让 Vite 解析。
5. **构建产物异常**：根在 dev/build 双路径，永远以 `build`+`preview` 为准排查。
6. **sourcemap**：生产用 `'hidden'` + 上传监控平台，既能定位又不泄露源码。

## 九、可直接用于项目的排障 checklist

- [ ] 遇到模块导出报错，先判断 CJS/ESM 与上下文，再调导入写法 / `optimizeDeps.include`。
- [ ] 依赖相关怪现象先试 `vite --force` / 删 `node_modules/.vite`。
- [ ] HMR 异常先看终端是 `hmr update` 还是 `page reload`，据此定位边界。
- [ ] 线上资源 404 第一个怀疑 `base`；资源引用没有手写源码绝对路径。
- [ ] 任何“dev 正常 build 异常”一律用 `build` + `preview` 复现，不用 dev 下结论。
- [ ] 生产构建开 `sourcemap: 'hidden'` 并把 `.map` 上传监控平台，不部署到公网。
