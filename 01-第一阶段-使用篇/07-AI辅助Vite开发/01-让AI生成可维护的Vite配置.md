# 01 · 让 AI 生成可维护的 Vite 配置

> 本节解决的真实工程问题：你对 AI 说「帮我写个 Vite 配置」，它三秒丢给你一份能跑的 `vite.config.ts`——但半年后没人敢动它：不知道每个选项为什么在、是哪版 API、删了会不会炸。**「能跑」和「可维护」是两回事**。本节给一套把 AI 从「能跑配置生成器」逼成「可维护配置协作者」的提问方法，并配一个采集项目上下文的脚本，让你每次都能给 AI 喂对料。
>
> 事实基线：2026 年中，Vite 8.1.x / Rolldown 1.1.x / Oxc。
>
> 边界：本节讲的是**怎么和 AI 协作产出配置**，不是 `vite.config` 各字段的逐项详解（那是 [01 核心使用 / 02 项目搭建与配置详解](../01-核心使用/02-项目搭建与vite.config配置详解.md) 的事）。

---

## 一、为什么「能跑的配置」是个陷阱

先看一段很典型的「AI 随手配置」。你问「帮我配置 Vite 分包和别名」，它给：

```js
// ❌ AI 常见输出：能跑，但是个维护黑洞
import { defineConfig } from 'vite'

export default defineConfig({
  resolve: { alias: { '@': '/src' } },
  build: {
    rollupOptions: {
      output: {
        manualChunks(id) {
          if (id.includes('node_modules')) return 'vendor'
        },
      },
    },
  },
})
```

这份配置在你机器上可能真能跑。但它藏了三颗雷：

1. **版本错位**：`manualChunks` 是 Rollup 时代的写法，Vite 8 的官方推荐是 `build.rolldownOptions.output.codeSplitting`（见 [05 章配置迁移](../05-版本差异与升级迁移/02-各版本升级要点与配置迁移.md)；注意别用早期 Rolldown 已废弃的过渡名 `advancedChunks`）。`rollupOptions` 在 Vite 8 走兼容层仍能用，但 AI 没告诉你「这是旧写法、有新写法」——你以为学到了 2026 的最佳实践，其实抄了 2023 的。
2. **取舍不明**：`alias` 用了绝对路径字符串 `/src`，在某些部署 base 下会出问题；`vendor` 一锅端会让所有第三方进一个巨包，首屏反而更慢。**AI 没说这些 trade-off**，你也就无从判断它适不适合你的项目。
3. **不可追溯**：半年后你看这份配置，完全不知道当初为什么这么配、能不能删。配置成了「祖传代码」。

> **核心认知**：AI 的输出质量上限，由你给它的**上下文**和**约束**决定。你只说「配个分包」，它就只能按训练语料里最高频（往往最旧）的写法给你一份「平均答案」。要可维护的配置，得换一种问法。

## 二、可维护配置的四条提问纪律

把「帮我写个配置」升级成下面四条，AI 的产出会肉眼可见地变好。

### 纪律 1：给足上下文（项目长什么样）

AI 不知道你的项目，你不说它就猜。至少给它这些：

- **运行时环境**：Node 版本、包管理器（npm/pnpm/yarn）、是否 monorepo。
- **Vite 与关键依赖版本**：`vite`、框架插件、用到的社区插件的**确切版本**。
- **项目类型**：SPA / MPA / SSR / 库模式？用什么框架？
- **已有配置**：把现有的 `vite.config` 和 `package.json` 贴给它，让它在你的基础上改，而不是凭空造一份覆盖你的。

> 本节配套的 `01-AI配置上下文包/scripts/collect-context.mjs` 就是干这件事的——一条命令把上面这些信息打成一段可直接粘给 AI 的「上下文块」，省得你手动找版本号。

### 纪律 2：锁版本（告诉它你在哪个时代）

这是 Vite 场景里**最重要**的一条。明确写：

> 「我用的是 **Vite 8.1**，请用 Vite 8 的官方推荐 API，不要用 Vite 5/6 的旧写法；如果某个写法在 Vite 8 已废弃或改名，请用新名字并标注。」

不锁版本，AI 默认会混用各版本 API（03 节专门讲这个坑）。锁了版本，它至少会往正确的时代靠。

### 纪律 3：要解释，不要只要代码

把「给我配置」改成：

> 「给我配置，并且**对每个非默认选项，用一句注释说明：它解决什么问题、默认行为是什么、这么配的代价是什么**。如果某个选项保持默认更好，请告诉我别配。」

这一句能逼出 AI 的「推理」，而推理才是你判断「该不该信」的依据。一个连自己为什么这么配都说不清的配置项，多半是它在凑数。

### 纪律 4：要求最小化（别塞默认值）

AI 特别爱「过度配置」——把一堆其实是默认值的选项写出来显得专业。明确要求：

> 「只写**和默认行为不同**的选项，默认就够用的不要写。配置越小越好维护。」

Vite 的哲学本就是「合理默认 + 按需覆盖」。一份好的 `vite.config` 往往只有寥寥几行，每一行都有存在的理由。

## 三、一个能直接用的提问模板

把上面四条拼起来，就是这个可复制的模板（配套 `01-AI配置上下文包/README.md` 也存了一份）：

```
我在配置一个 Vite 项目，请帮我写/改 vite.config。

【环境与版本】
- Node: v22.12.0
- 包管理器: pnpm
- vite: 8.1.2
- 框架: React 19 + @vitejs/plugin-react 6.x
- 项目类型: SPA，会部署到 CDN 子路径 /app/

【现有配置】
（贴 vite.config + package.json 的 dependencies）

【我想达成的目标】
1. 按路由做代码分割，第三方库单独成块但不要一锅端
2. @ 指向 src
3. 生产环境去掉 console

【约束】
- 必须用 Vite 8 官方推荐 API，旧写法请改新名并标注（如 rollupOptions→rolldownOptions、manualChunks→codeSplitting）
- 每个非默认选项加一行注释：解决什么问题、默认行为、代价
- 只写和默认不同的选项，默认够用的不要写
- 不确定的地方请明说「我不确定，请查官方文档确认」，不要编
```

最后那条「不确定就说不确定」很关键——它给了 AI「示弱」的许可，能显著降低硬编的概率。

## 四、好配置长什么样：带取舍说明的范例

用上面的模板问出来，理想产出应该像这样（配套 `01-AI配置上下文包/vite.config.annotated.js` 存了完整可读版本）：

```js
import { defineConfig } from 'vite'
import react from '@vitejs/plugin-react'

export default defineConfig({
  // 部署到 CDN 子路径，资源 URL 需带前缀；本地 dev 不受影响。
  // 代价：忘了改 base 会导致线上资源 404，是上线最常见的低级错。
  base: '/app/',

  plugins: [react()],

  resolve: {
    // 用对象式别名而非裸字符串路径，配合 import.meta 解析更稳；
    // 注意要和 tsconfig 的 paths 保持一致，否则 IDE 与构建会各行其是。
    alias: { '@': new URL('./src', import.meta.url).pathname },
  },

  build: {
    // Vite 8 推荐的分包入口在 rolldownOptions.output.codeSplitting（取代旧的 rollupOptions.output.manualChunks）。
    // 按「分组」声明，而不是手写函数，可读性和稳定性都更好。
    // 代价：分得太细会增加请求数，要结合产物分析（08 章）调，而不是拍脑袋。
    rolldownOptions: {
      output: {
        codeSplitting: {
          groups: [
            { name: 'react-vendor', test: /node_modules\/(react|react-dom)\// },
          ],
        },
      },
    },
  },

  esbuild: {
    // 仅生产去掉 console/debugger；dev 保留方便调试。
    // 注意：Vite 8 转译由 Oxc 接管，但这个选项语义仍兼容。
    drop: process.env.NODE_ENV === 'production' ? ['console', 'debugger'] : [],
  },
})
```

对比第一节那份「黑洞配置」，差别不在代码多漂亮，而在**每一行你都能读懂、能判断、能改**。这才叫可维护。

> 注意：上面这份范例也**不是终点**——`codeSplitting` 到底怎么分、`base` 写什么，仍要结合你项目的产物分析和部署方式定。旧文章里常见的顶层 `esbuild.drop` 在 Vite 8 已属于历史兼容选项：常规转译由 `oxc` 接管；如果你确实要生产去掉 `console/debugger`，优先用当前压缩器/插件链路提供的能力，并用产物搜索验证。AI 给的是「带说明的草稿」，你的活是「带判断地定稿」。



## 五、动手：用上下文采集脚本喂对料

配套代码：[第一阶段-使用篇/07-AI辅助Vite开发/01-AI配置上下文包/](https://github.com/XY0987/vite_brochure_code_public/tree/main/第一阶段-使用篇/07-AI辅助Vite开发/01-AI配置上下文包/)

```bash
cd vite_brochure_code_public/第一阶段-使用篇/07-AI辅助Vite开发/01-AI配置上下文包
node scripts/collect-context.mjs
```

它会扫描当前（或指定）项目，打印一段可直接粘给 AI 的上下文块：Node 版本、包管理器、`vite` 与插件的**实际安装版本**、项目类型推断、现有 `vite.config` 摘要。把这段贴进上面的模板「【环境与版本】」「【现有配置】」处，AI 就不用猜了。

```bash
# 也可以对你自己的真实项目跑：
node scripts/collect-context.mjs /path/to/your/project
```

观察点：脚本读的是 `node_modules/.../package.json` 里的**真实版本**，而不是 `package.json` 里写的 `^8.1.0` 这种范围——这点很重要，AI 需要知道你**实际装了哪个版本**，而不是你「希望装哪个范围」。

## 六、本节小结

- **「能跑」≠「可维护」**：AI 随手给的配置常踩三雷——版本错位、取舍不明、不可追溯。
- **输出质量由输入决定**：四条提问纪律——① 给足上下文（环境/版本/类型/现有配置）；② 锁版本（明确 Vite 8、旧写法改新名）；③ 要解释（每个选项说清问题/默认/代价）；④ 要最小化（不写默认值）。
- **用模板固化**：把四条拼成可复制的提问模板，最后加一句「不确定就说不确定」。
- **好配置的标准**：不是代码漂亮，而是**每一行你都能读懂、判断、修改**。
- AI 给的是「带说明的草稿」，定稿仍要靠你结合产物分析与部署实际——这正是下一节排错、03 节避坑、04 节校验要接力的事。

## 七、可直接用于项目的 checklist

- [ ] 给 AI 提配置需求前，先跑上下文采集脚本，把真实环境/版本贴进去。
- [ ] 提问里**明确写出 Vite 大版本**，并要求「旧写法改新名并标注」。
- [ ] 要求 AI 对每个非默认选项给出「解决什么/默认行为/代价」三句话。
- [ ] 要求「只写与默认不同的选项」，拿到配置后删掉所有其实是默认值的项。
- [ ] 对 `base`、分包策略、`alias` 这类「和部署/产物强相关」的选项，不照抄，结合自己项目定。
- [ ] 配置里每个选项都问自己一遍「半年后的我看得懂为什么它在这吗」，看不懂就补注释或删掉。
- [ ] 凡 AI 标了「不确定」的地方，去官方文档核对后再落地（校验方法见 [04 节](./04-人必须掌握的校验方法.md)）。
