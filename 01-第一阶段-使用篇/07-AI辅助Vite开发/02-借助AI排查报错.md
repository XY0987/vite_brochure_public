# 02 · 借助 AI 排查报错

> 本节解决的真实工程问题：Vite 构建/启动炸了一屏红字，你复制粘贴给 AI「这个报错怎么解决」，结果它给了五个互相矛盾的方案，挨个试还是不行，越问越乱。问题不在 AI——**在你给它的信息不足以定位根因**。本节给一套「把报错组织成有效提问」的方法，并配一个一键采集诊断信息、生成可粘贴提问块的脚本。
>
> 事实基线：2026 年中，Vite 8.1.x / Rolldown 1.1.x / Oxc。
>
> 边界：本节讲的是**怎么把报错喂给 AI 才能命中根因**，各类报错本身的成因与修法见 [01 核心使用 / 09 真实工程排障专题](../01-核心使用/09-真实工程排障专题.md)。两节配合食用：那节教你「病理」，本节教你「怎么向 AI 描述病情」。

---

## 一、为什么「贴报错问 AI」经常翻车

考虑这条经典报错：

```
The requested module '/node_modules/.vite/deps/some-lib.js?v=abc' does not provide an export named 'foo'
```

直接把这一行丢给 AI，它能给你的也就是「检查导出名」「试试 optimizeDeps.include」——一堆**泛泛的可能性**。因为它缺三类关键信息：

1. **环境事实**：你的 Node 版本、Vite 版本、`some-lib` 版本是多少？这决定了根因到底是 CJS/ESM 互操作、还是预构建缓存、还是版本 bug。
2. **触发条件**：这报错是 `dev` 时、`build` 时、还是 `preview` 时出现？是首次启动还是改了依赖后？SSR 还是 client？
3. **完整上下文**：完整的报错栈（不是被你截断的一行）、相关的 `vite.config`、`package.json` 依赖。

> **核心认知**：排错的本质是**缩小可能性空间**。信息越全，AI（和你）能排除的可能性越多，离根因越近。只给一行报错，等于让 AI 在全部可能性里盲猜——它当然只能给你「试试这个、试试那个」。

## 二、有效提问的五要素（SCROL）

把报错组织成下面五块，AI 命中率会陡增。记成 **SCROL**：


| 要素            | 内容                              | 为什么 AI 需要它                 |
| ------------- | ------------------------------- | -------------------------- |
| **S**tack     | 完整报错栈，不截断                       | 栈帧里藏着真正出错的模块/插件，截断就丢了线索    |
| **C**ommand   | 触发命令与阶段（dev/build/preview/test） | 同一报错在不同阶段根因不同（如双引擎时代的行为差异） |
| **R**eproduce | 最小复现步骤 / 是否能稳定复现                | 偶发和必现的排查路径完全不同             |
| **O**verview  | 环境总览：Node/Vite/相关依赖版本、OS、包管理器   | 锁定是不是版本/平台特定问题             |
| **L**ist      | 你**已经试过**什么、结果如何                | 防止 AI 再给你试过的无效方案，逼它换思路     |


最后这个 **L（已试列表）** 最常被忽略，却最有用——它把对话从「AI 重复建议、你重复否定」推进到「排除了这些，那根因更可能是……」。

## 三、把报错喂对：三个反模式 vs 正确做法

### 反模式 1：只贴一行 / 只贴最后一行

报错栈的**第一行**往往是最终现象，**真正的源头常在中间的栈帧**（哪个插件、哪个模块）。

- ❌ 只贴 `does not provide an export named 'foo'`
- ✅ 贴从 `[vite]` / `[plugin xxx]` 开头到栈底的完整块，包括 `Plugin:`、`File:` 这些字段。

### 反模式 2：截图代替文本

把报错截图发给 AI（即便它能读图）会丢失可复制性，也容易漏掉滚动区外的内容。

- ✅ 复制**文本**。终端报错全选复制，浏览器控制台右键 "Copy" 整条。

### 反模式 3：不说版本，或只说 `package.json` 里的范围

`"vite": "^8.0.0"` 不等于你装的是哪个版本。Vite 这种快速迭代的工具，`8.1.0` 和 `8.1.5` 可能就差一个关键修复。

- ✅ 给**实际安装版本**（`npm ls vite` 或本节脚本输出的），不是 `package.json` 里的范围。

## 四、一个能直接用的排错提问模板

把 SCROL 拼起来（配套 `02-报错复现与诊断采集/README.md` 也存了一份）：

```
我的 Vite 项目报错了，请帮我定位根因（不要直接给修法，先帮我判断最可能的原因和如何确认）。

【触发命令与阶段 Command】
- 命令: pnpm build
- 阶段: 生产构建（dev 正常，仅 build 报错）

【环境总览 Overview】
- OS: macOS 14 (arm64)
- Node: v22.12.0
- 包管理器: pnpm 9.x
- vite: 8.1.2（实际安装版本，非范围）
- 相关依赖: some-lib 3.2.0（CommonJS 包）

【完整报错栈 Stack】
（这里贴完整的、不截断的报错，含 Plugin/File 字段）

【最小复现 Reproduce】
- 能稳定复现：删 node_modules + 重装后 build 必现
- 触发点：上周升级 some-lib 从 2.x 到 3.x 后开始

【我已经试过 List】
1. 删 node_modules/.vite 重启 —— 无效
2. optimizeDeps.include 加 some-lib —— dev 好了，build 仍报错
3. 改成具名导入 —— 报错不变

请基于以上信息：① 给出最可能的 1-2 个根因；② 每个根因给一个「如何确认是它」的验证步骤；③ 确认后再给修法。
```

注意最后那句「**先判断根因、给确认方法，再给修法**」——这把 AI 从「方案喷射器」拨回「诊断助手」，逼它先推理。这也呼应了第三阶段要讲的「用最小复现和事实建立确定性」。

## 五、动手：一键生成诊断信息块

手动收集 Node/Vite/依赖版本很烦，配套脚本帮你打包好。

配套代码：[第一阶段-使用篇/07-AI辅助Vite开发/02-报错复现与诊断采集/](https://github.com/XY0987/vite_brochure_code_public/tree/main/第一阶段-使用篇/07-AI辅助Vite开发/02-报错复现与诊断采集/)

```bash
cd vite_brochure_code_public/第一阶段-使用篇/07-AI辅助Vite开发/02-报错复现与诊断采集
node scripts/collect-diagnostics.mjs
```

它会输出一段填好「Overview」的诊断块（OS / Node / 包管理器 / Vite 与相关依赖实际版本），你把报错栈和「已试列表」补进去就是一条完整的 SCROL 提问。

### 配套：一个真能复现的报错现场

为了让你练手「描述病情」，demo 里放了一个**确定性可复现**的 CJS/ESM 互操作报错现场（这是 Vite 依赖预构建报错最常见的病根之一）：

```bash
node scripts/reproduce.mjs
```

它会真实地抛出「具名导入一个 CommonJS 包失败」的错误。然后你可以：

```bash
node scripts/collect-diagnostics.mjs   # 采集环境
# 把上面的报错 + 环境块 拼成 SCROL，体会「信息全」和「只贴一行」的差别
```

观察点：同样一个报错，当你带上「这是个 CJS 包 + Node 版本 + 触发阶段」时，根因（CJS/ESM 互操作）几乎一眼可辨；而只贴报错那一行时，它看起来像十几种问题中的任意一种。**这就是信息组织带来的定位效率差。**

## 六、AI 排错的正确姿势：让它帮你「缩小」，你来「确认」

最后强调一个协作分工，避免把 AI 当甩锅对象：

- **AI 擅长**：从你给的完整信息里快速列出「可能的根因清单」、回忆某个报错的常见成因、提示你「该去看哪个日志/哪个配置」。
- **AI 不擅长（也不该让它干）**：替你**确认**根因。确认必须靠你在真实环境里跑——删缓存重试、改一个变量看变化、加日志、打断点。
- **铁律**：AI 说「应该是 X」时，先问它「我怎么验证确实是 X」，验证通过再动手改。**没验证就改，是在用 AI 的猜测赌你的时间。**（系统的校验方法见 [04 节](./04-人必须掌握的校验方法.md)。）

## 七、本节小结

- **排错本质是缩小可能性空间**：只贴一行报错 = 让 AI 盲猜；信息越全，能排除的越多。
- **有效提问五要素 SCROL**：Stack（完整栈）、Command（命令/阶段）、Reproduce（复现）、Overview（环境版本）、List（已试列表）。其中「已试列表」最被忽略也最有用。
- **三个反模式**：只贴一行、用截图、不报实际版本——分别对应丢线索、丢可复制性、丢版本事实。
- **用模板固化**，并要求 AI「先判根因 + 给确认方法，再给修法」，把它从方案喷射器拨回诊断助手。
- **分工铁律**：AI 帮你缩小，你来确认；AI 说「应该是 X」先问「怎么验证 X」，验证过再改。

## 八、可直接用于项目的 checklist

- [ ] 向 AI 报错前，先跑诊断采集脚本拿到「实际版本 + 环境」块。
- [ ] 贴**完整报错栈**，保留 `Plugin:`/`File:` 等字段，不要只贴第一行。
- [ ] 用文本而非截图，保证可复制、不漏内容。
- [ ] 写清楚触发**命令与阶段**（dev/build/preview/test、client/SSR）。
- [ ] 列出「我已经试过什么、结果如何」，逼 AI 换思路。
- [ ] 要求 AI「先给根因 + 确认方法，再给修法」。
- [ ] AI 给的根因，自己在真实环境验证通过后才动手改；改完确认报错确实消失且没引入新问题。
