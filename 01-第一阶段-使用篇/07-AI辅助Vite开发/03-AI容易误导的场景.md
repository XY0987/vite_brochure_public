# 03 · AI 容易误导的场景

> 本节解决的真实工程问题：AI 给 Vite 答案时语气总是很自信，但在某几类问题上它**特别容易自信地错**。如果你不知道雷区在哪，就会把过时写法、张冠李戴的 API 当成最佳实践抄进项目。本节给一张「AI 在 Vite 上最常翻车」的风险地图，并配一个能扫出配置里 AI 式过时写法的体检脚本。
>
> 事实基线：2026 年中，Vite 8.1.x / Rolldown 1.1.x / Oxc。
>
> 边界：本节讲**哪些场景要警惕 AI**（风险地图），具体怎么验证某个答案对不对，见 [04 节](./04-人必须掌握的校验方法.md)。

---

## 一、为什么偏偏是 Vite，AI 特别容易错

不是 AI 笨，是 Vite 这个领域踩中了 LLM 的两个软肋：

1. **语料时间分布失衡**：互联网上关于 Vite 的文章、Stack Overflow 回答、GitHub issue，**绝大多数写于 Vite 2~5 时代**（2021–2023）。而 Vite 在 2024–2026 经历了 6→7→8 的剧烈演进（Environment API、Rolldown、Oxc）。AI 训练语料里「旧写法」的密度远高于「新写法」，于是它的「默认答案」天然偏旧。
2. **版本断点密集且 API 改名**：`rollupOptions`→`rolldownOptions`、`manualChunks`→`codeSplitting`（中间还有个已废弃的过渡名 `advancedChunks`）、双引擎→单引擎……这些改名和语义迁移，让 AI 极易把不同版本的 API **混搭**成一份「看起来对、其实没有任何一个版本这么用」的配置。

> **核心认知**：AI 在 Vite 上的错误**不是随机分布的**，而是高度集中在「版本演进剧烈处」。知道这张地图，你就知道哪些答案可以放心用、哪些必须重点验。

## 二、四类高频误导场景

### 场景 1：版本 API 混淆（最高频）

AI 经常把不同 Vite 版本的 API 拼在一起。典型症状：

```js
// ❌ AI 混搭：rolldownOptions（V8 新名）里却套了 manualChunks（旧函数式写法）
export default defineConfig({
  build: {
    rolldownOptions: {
      output: {
        manualChunks(id) { /* ... */ }, // V8 推荐的是 codeSplitting
      },
    },
  },
})
```

- **为什么会这样**：它知道「V8 改叫 rolldownOptions」（学到了新词），但分包函数仍按语料里最高频的 `manualChunks` 给（没学到配套的新写法）。结果是个**缝合怪**。
- **怎么识别**：凡是涉及「改过名的 API」（见 [05 章配置迁移对照](../05-版本差异与升级迁移/02-各版本升级要点与配置迁移.md)），都要警惕新旧混用。
- **正解**：Vite 8 分包优先 `build.rolldownOptions.output.codeSplitting`；`rollupOptions`/`manualChunks` 走兼容层能跑，但不是 8 的推荐写法；`advancedChunks` 是早期 Rolldown 的过渡名、已 deprecated。

### 场景 2：过时配置（看起来很专业的旧答案）

AI 会自信地给出在新版本里**已废弃、已默认、或已改默认值**的配置：

- 推荐你手动开 `build.cssCodeSplit`、`optimizeDeps` 的某些项——而它们在新版早已是默认或行为已变。
- 给出 Vite 4/5 时代的 `server.middlewareMode` 写法、SSR API 形态——而 Environment API（V6+）已经重构了这块（见 [04 章 EnvironmentAPI](../04-多环境与工程化场景/01-EnvironmentAPI落地多环境多运行时.md)）。
- 让你装某个在 V8 已被内置 Oxc/Rolldown 取代的插件（如某些单独的压缩/转译插件）。

> 识别要点：AI 给的配置「能跑」不代表「该写」。很多旧配置在新版是**冗余的默认值**或**已被内置能力取代**——参见 [01 节](./01-让AI生成可维护的Vite配置.md)讲的「只写和默认不同的选项」。

### 场景 3：插件兼容性误判

这是 Rolldown 时代的新坑。AI 容易：

- **假设所有 Rollup 插件都能在 Vite 8 无缝用**。事实是：Rolldown 兼容 Rollup 插件 **API**，但依赖 Rollup **内部实现**的插件可能失效（见 [05 章 rolldown-vite 隔离层](../05-版本差异与升级迁移/03-Vite8单打包器解锁的新能力.md) 与 [06 章](../06-打包工具横向对比/README.md)）。
- **推荐已停止维护或已被取代的插件**（如 esbuild 系的某些转译插件，在 V8 由 Oxc 接管后不再需要）。
- **混淆 Vite 插件和 Rollup 插件的钩子能力**——把只在某一侧生效的钩子说成通用的（钩子模型见 [03 章 Rollup 钩子](../03-插件与生态/02-Rollup基础钩子模型与Vite的关系.md)）。

> 识别要点：AI 推荐任何插件时，问它「这个插件在 Vite 8 + Rolldown 下验证过吗？它依赖 Rollup 内部实现吗？」——它答不上来的，就去插件仓库看 issue 和最近更新时间。

### 场景 4：SSR / edge 环境差异忽略

AI 默认按「单一 client 构建」思考，容易忽略多环境/多运行时的差异：

- 给的代码在 client 跑得好，搬到 SSR 就因为**外部化（externalize）、条件导入、环境变量泄露**而炸（见 [04 章 SSR 工程坑位](../04-多环境与工程化场景/03-SSR工程坑位排查手册.md)）。
- 忽略 **edge runtime** 没有 Node 内置模块（`fs`/`path`），给的方案在 edge 直接崩。
- 不区分「dev 的 SSR」和「build 的 SSR」行为差异，把 dev 能跑当成生产没问题。

> 识别要点：凡涉及 SSR/edge，先明确告诉 AI「这是 SSR / edge 环境，不能用 Node 内置模块 / 注意外部化」，否则它默认按 client 给，且不会主动提醒你环境差异。

## 三、一张速查：风险地图


| 误导场景        | 触发信号（看到这些要警惕）                                              | 一句话正解方向                                              |
| ----------- | ---------------------------------------------------------- | ---------------------------------------------------- |
| 版本 API 混淆   | 配置里出现改过名的 API（rollupOptions/manualChunks/advancedChunks 等） | 锁定 V8，用 rolldownOptions + output.codeSplitting，别新旧混用 |
| 过时配置        | 手动配了「听起来该有但其实是默认/已废弃」的项                                    | 只留和默认不同的；查该项在 V8 是否仍需要                               |
| 插件兼容性误判     | 「这个 Rollup 插件直接装上就行」                                       | 确认它在 V8+Rolldown 验证过、不依赖 Rollup 内部实现                 |
| SSR/edge 忽略 | client 代码被直接挪到服务端/边缘                                       | 显式声明环境，注意外部化/条件导入/无 Node 内置模块                        |


> 这四类的共同根因都是 **「AI 的语料偏旧 + Vite 版本演进快」**。所以最有效的防御就是 [01 节](./01-让AI生成可维护的Vite配置.md)那条：**永远在提问里锁死 Vite 大版本**。

## 四、动手：给配置做一次「AI 式过时写法」体检

配套代码：[第一阶段-使用篇/07-AI辅助Vite开发/03-AI误导对比/](https://github.com/XY0987/vite_brochure_code_public/tree/main/第一阶段-使用篇/07-AI辅助Vite开发/03-AI误导对比/)

demo 里放了两份配置：`examples/ai-stale.config.js`（AI 常给的过时/混搭写法）和 `examples/correct.config.js`（Vite 8 正解），以及一个体检脚本：

```bash
cd vite_brochure_code_public/第一阶段-使用篇/07-AI辅助Vite开发/03-AI误导对比
node scripts/check-stale-config.mjs examples/ai-stale.config.js
node scripts/check-stale-config.mjs examples/correct.config.js
```

脚本用规则匹配扫出常见的 AI 式过时/可疑写法（`manualChunks`、裸 `rollupOptions`、被 Oxc 取代的转译插件、写死的默认值等），并对每条给出「为什么可疑 + V8 正解方向」。

```bash
# 也可以体检你自己项目的配置：
node scripts/check-stale-config.mjs /path/to/your/vite.config.js
```

观察点：对 `ai-stale.config.js` 它会亮一串告警，对 `correct.config.js` 基本清白。这个脚本不是要替你做决定——它是**把「该警惕的地方」自动标出来**，提醒你去 [04 节](./04-人必须掌握的校验方法.md)的方法逐条核实。它本质是「AI 风险地图」的可执行版。

> 注意脚本的定位：它做的是**静态规则提示**，不可能覆盖所有情况，也会有误报（比如你确实有理由用 `rollupOptions` 兼容某插件）。它的价值是**降低漏检**，把人的注意力引到高风险处，而不是给配置打分。

## 五、本节小结

- AI 在 Vite 上的错误**不是随机的**，集中在「版本演进剧烈处」——根因是「语料偏旧 + Vite 迭代快」。
- 四类高频误导：**版本 API 混淆**（新旧 API 缝合）、**过时配置**（废弃/默认/被取代的项）、**插件兼容性误判**（假设 Rollup 插件都能用）、**SSR/edge 差异忽略**（按 client 思维给方案）。
- 每类都有「触发信号」，看到就该重点验，而不是照抄。
- 最有效的通用防御：**提问时锁死 Vite 大版本**（呼应 01 节）。
- 体检脚本把风险地图变成可执行工具：自动标出可疑写法，但只做提示、不替你决策。

## 六、可直接用于项目的 checklist

- [ ] 看到 AI 配置里出现「改过名的 API」（rollupOptions/manualChunks 等），先去 05 章对照表确认 V8 正解。
- [ ] 对 AI 手动配的每个选项，确认它在 V8 是否仍必要（不是默认、不是已废弃、不是已被内置取代）。
- [ ] AI 推荐任何插件，核实它「在 Vite 8 + Rolldown 验证过、不依赖 Rollup 内部实现、近期仍维护」。
- [ ] 涉及 SSR/edge 的需求，提问时**显式声明环境**，并自查外部化/条件导入/Node 内置模块假设。
- [ ] 用体检脚本扫一遍最终配置，对每条告警逐项核实（确认是误报再保留）。
- [ ] 凡 AI 答案落在以上四类高风险区，一律走 [04 节](./04-人必须掌握的校验方法.md)的校验流程后再上线。
