# 04 · 人必须掌握的校验方法

> 本节解决的真实工程问题：AI 给的配置和排错方案听起来都很对，但「听起来对」不能上线。03 节告诉了你 AI 在哪几类问题上最容易错，本节给出**确认对错的四种武器**——最小复现、官方文档、源码断点、构建产物验证。这是工程师在 AI 时代**唯一不可外包**的能力：对结果的最终确定性，必须由你建立。
>
> 事实基线：2026 年中，Vite 8.1.x / Rolldown 1.1.x / Oxc。
>
> 边界：本节是第一阶段的收口，也是第三阶段「AI 时代的工程判断」的使用层预演——这里练「怎么验」的手感，第三阶段升华为可迁移的方法论。

---

## 一、为什么校验不可外包

AI 能生成配置、能解释源码、能列出报错的可能原因。但有一件事它**做不到、也不该让它做**：替你确认「在你的真实环境里，这个答案到底对不对」。

原因很简单：AI 给的是**基于概率的最可能答案**，不是**基于你这台机器、这个版本、这份代码的事实**。03 节已经说明，它在 Vite 上的错误高度集中在版本演进处。所以：

> **核心认知**：AI 负责「提出假设」，你负责「证实假设」。证实必须落到**可观测的事实**上——能跑的复现、白纸黑字的文档、断点处真实的运行值、构建出来的真实产物。这四样，构成你的「确定性来源」。

下面四种武器，从「最轻」到「最重」排列。日常按需取用，不必每次全上。

## 二、武器一：最小复现（成本最低、最该先做）

**最小复现（minimal reproduction）**：把问题剥离到一个尽可能小、只保留触发条件的项目里。它是校验的第一武器，因为：

- 能**证伪 AI 的归因**：AI 说「是 some-lib 的问题」，你在最小复现里去掉 some-lib 还报错，就证明它错了。
- 能**隔离变量**：真实项目里几十个依赖互相干扰，最小复现里只剩一两个变量，一改一看就知道因果。
- 能**复用**：[02 节](./02-借助AI排查报错.md)讲过，最小复现本身就是给 AI 的最佳输入。

实操要点：

1. 用 `npm create vite@latest` 起一个干净项目（锁定 Vite 8）。
2. 只加**触发问题的最小依赖和代码**，每加一样就跑一次，直到问题出现。
3. 问题出现的那一步，就是根因所在。

> 配套 `04-校验工具箱/scripts/new-min-repro.mjs` 能帮你生成一个最小复现的骨架目录和「记录每一步改动」的清单模板，让复现过程可追溯。

## 三、武器二：官方文档（事实的第一来源）

AI 的语料偏旧（03 节），而**官方文档是当前版本的事实基准**。校验顺序应该是：

- AI 说「Vite 8 用 X 配置」→ 去 [vitejs.dev](https://vite.dev) 对应版本文档搜 X，确认它**存在、且语义一致**。
- 特别核对**改过名的 API**：文档里搜不到 AI 给的名字（如还在用 `manualChunks` 当推荐），基本就是旧写法。
- 看文档的**版本标注与 changelog**：Vite 文档会标某特性的引入/废弃版本，这是判断「AI 给的是不是当前写法」的硬依据。

> 心法：**让 AI 给「该查什么」，自己去查「是什么」**。比如问 AI「Vite 8 分包配置叫什么、在文档哪一节」，拿到关键词后自己去官方文档核实——既用了 AI 的检索能力，又用文档兜住了事实。

## 四、武器三：源码断点（看到真实运行值）

当文档说不清、行为很诡异时，**断点是终极裁判**——它让你看到代码在你的环境里**实际**怎么走、变量**实际**是什么值。这也是本小册第二阶段的核心方法论（「不是读源码，是调源码」）在使用阶段的预演。

使用层最常用的两个轻量断点场景：

1. **在自己的** `vite.config` **/ 插件钩子里打断点或** `console.log`：验证 AI 说的「这个钩子会在 build 时触发」「这个选项会改变某变量」是否属实。
  ```js
   // 在配置里验证 AI 关于「command 区分 dev/build」的说法
   export default defineConfig(({ command, mode }) => {
     console.log('[verify] command =', command, ' mode =', mode) // 亲眼看到，而不是听 AI 说
     return { /* ... */ }
   })
  ```
2. **用** `--debug` **/** `DEBUG` **看 Vite 内部日志**：`vite build --debug` 会打印插件、解析、转换的真实流程，用来核对 AI 对「内部发生了什么」的描述。

> 断点的价值在于：它把「AI 说应该这样」变成「我看到确实这样（或不是这样）」。看到一次胜过听十遍。深入的源码断点（dev server、HMR、插件容器）是第二阶段的主场。

## 五、武器四：构建产物验证（结果的最终对账）

配置类的 AI 答案，最终都要落到**产物**上对账。AI 说「这样配会把 react 单独分包」「这样配生产会去掉 console」——**别信，去** `dist/` **里查**。

常见对账项：

- **分包是否真的生效**：`dist/assets/` 里是否真出现了独立的 vendor chunk？还是依旧一锅端？
- **压缩/去除是否生效**：产物里搜 `console.log`，看生产构建是否真去掉了。
- **资源路径是否正确**：`base` 配了之后，产物里的资源 URL 前缀对不对（线上 404 的高发区）。
- **体积是否如预期**：结合 [08 章产物分析](../01-核心使用/08-性能优化产物分析与报错排查手册.md)的可视化，看分包是否真的优化了首屏。

> 配套 `04-校验工具箱/scripts/verify-build.mjs` 演示如何用脚本对 `dist/` 自动对账：检查 chunk 数量与命名、扫描产物里是否残留 `console`、校验资源前缀。把它接进 CI，就能**自动拦住「AI 配置看起来对、产物其实没生效」的情况**。

## 六、把四种武器串成一条校验流水线

不是每次都四样全上，而是按「成本递增」依次升级，能在前一步定论就停：

```
AI 给出答案/配置
      │
      ▼
①最小复现：能不能在干净环境复现/证伪？  ──能定论──▶ 完
      │ 还不确定
      ▼
②官方文档：API 名/语义/版本对得上吗？    ──能定论──▶ 完
      │ 文档说不清
      ▼
③源码断点/debug：实际运行值/流程是什么？  ──能定论──▶ 完
      │ 涉及构建结果
      ▼
④产物验证：dist 里真的如它所说吗？        ──────────▶ 上线/接 CI
```

这条流水线就是「人对 AI 答案负责」的具体落地。它不慢——大多数问题在 ① 或 ② 就定论了；真正诡异的才需要 ③④。

配套代码：[第一阶段-使用篇/07-AI辅助Vite开发/04-校验工具箱/](https://github.com/XY0987/vite_brochure_code_public/tree/main/第一阶段-使用篇/07-AI辅助Vite开发/04-校验工具箱/)

```bash
cd vite_brochure_code_public/第一阶段-使用篇/07-AI辅助Vite开发/04-校验工具箱

# 武器一：生成一个可追溯的最小复现骨架
node scripts/new-min-repro.mjs 我的预构建报错

# 武器四：对一个产物目录做自动对账（demo 自带 示例产物/ 可直接跑）
node scripts/verify-build.mjs 示例产物
```

`verify-build.mjs` 会对 `示例产物/` 报告：有几个 chunk、是否做了 vendor 分离、产物里是否残留 `console`、资源前缀是否一致。你可以故意改坏 `示例产物` 里的内容，再跑一次，看校验如何亮红——体会「产物对账」怎么抓住 AI「嘴上说生效、实际没生效」的情况。

```bash
# 对你真实项目：先 vite build，再指向真实 dist
node scripts/verify-build.mjs /path/to/your/project/dist
```

观察点：这套脚本不依赖 AI、不依赖网络，全是对**客观事实（文件、内容）**的检查。这正是校验的精髓——**确定性来自可观测的事实，不来自任何人（或 AI）的断言。**

## 八、本节小结

- **校验不可外包**：AI 提出假设，你证实假设；证实必须落到可观测的事实上。
- **四种武器（成本递增）**：① 最小复现（先做，证伪/隔离变量）；② 官方文档（事实第一来源，重点核对改名 API）；③ 源码断点/`--debug`（看到真实运行值）；④ 产物验证（结果最终对账）。
- **心法**：让 AI 给「该查什么」，自己去查「是什么」；让 AI 说「应该这样」，自己看「实际这样」。
- **串成流水线**：按成本依次升级，能在前一步定论就停，大多数问题在复现/文档阶段就解决。
- 这套「用事实建立确定性」的手感，正是第三阶段「AI 时代的工程判断」要升华的核心——**这也是本册立项的初衷：AI 替代不了的，正是人对确定性的最终负责。**

## 九、可直接用于项目的 checklist

- [ ] 拿到 AI 的关键答案/配置，先想「我用哪种武器验它最省事」。
- [ ] 诡异问题先做**最小复现**，每改一步记录，定位到根因那一步。
- [ ] 涉及 API 名称/语义，去**官方文档**核对当前版本，特别留意改过名的 API。
- [ ] 行为说不清时，在配置/钩子里打 `console.log` 或用 `vite build --debug` 看**真实流程**。
- [ ] 所有配置类答案，最终去 `dist/` **对账产物**：分包/压缩/路径是否真的如它所说。
- [ ] 把产物校验脚本接进 CI，自动拦截「配置看起来对、产物没生效」。
- [ ] 牢记：上线的依据是**你验证过的事实**，不是 AI（或任何人）的断言。
