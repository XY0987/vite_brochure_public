# 01 · 框架插件集成机制：Vue / React / Svelte 是怎么接进 Vite 的

> 本节解决的真实工程问题：为什么用 Vite 写 React/Vue 必须装一个 `@vitejs/plugin-*`，不装会怎样？为什么「改一个组件，浏览器只更新这个组件、不刷新整页」这种丝滑体验是插件给的，而不是 Vite 自带的？当 HMR 突然退化成整页刷新、或 JSX/`<template>` 报 “Failed to parse source” 时，到底是哪一环出了问题？理解框架插件的集成机制，你才能从「装上能跑」升级到「出问题能定位」。

事实基线：2026 年中，Vite 8.x（默认 Rolldown 打包器、Oxc 转译）。

---

## 一、先认清一个事实：Vite 不认识框架

很多人以为「Vite 支持 Vue/React」，准确说法是：**Vite 本身只认识标准的 JS / TS / CSS / 静态资源，它对 `.vue`、`.jsx`、`.svelte` 一无所知**。

浏览器更不认识。浏览器只能执行标准 JavaScript，你给它一段：

```jsx
function App() {
  return <h1>Hello</h1>;   // 这不是合法 JS，浏览器会直接报语法错误
}
```

或者一个 `.vue` 单文件组件（里面混着 `<template>`、`<script>`、`<style>`）——浏览器无从下手。

那中间这层「把框架语法翻译成浏览器能跑的 JS」的活儿，谁干？**框架插件。** 这就是为什么：

- 写 React 默认装 `@vitejs/plugin-react`（负责把 JSX 翻译成浏览器能跑的 JS，并接入 React 热更新；SWC 是另一套 JS/TS 编译器，只有项目已有 SWC 配置/插件、或团队明确要统一到 SWC 编译链路时，才换 `@vitejs/plugin-react-swc`）；
- 写 Vue 要装 `@vitejs/plugin-vue`；
- 写 Svelte 要装 `@sveltejs/vite-plugin-svelte`。

不装插件，Vite 会把 `.jsx`/`.vue` 当普通文件原样交给浏览器，于是你会看到语法错误或 “Failed to parse source”。

## 二、插件干的三件事

抛开各框架细节，所有框架插件本质上都在 Vite 的钩子里做同样三件事。回忆 [01 核心使用](../01-核心使用/README.md) 讲过的 dev 请求链路 `resolveId → load → transform`，框架插件主要挂在 **`transform`** 这一环：

### 1. 编译：框架语法 → 标准 JS

这是最核心的一步。插件在 `transform` 钩子里，把组件源码交给对应的编译器：

- **Oxc**：一套用 Rust 写的 JavaScript / TypeScript 工具链，Vite 8 里的 React 插件用它来做部分 React 开发转换，比如 Fast Refresh 相关处理；
- **SWC**：也是一套用 Rust 写的 JavaScript / TypeScript 编译器，很多工具会用它来做 TS/JSX 转换、压缩等。

| 框架 | 编译器 | 做的事 |
|---|---|---|
| React | **Oxc**（Vite 8 的 `@vitejs/plugin-react` v6 用 Oxc 做 Fast Refresh transform；SWC 是可选变体） | JSX → `React.createElement` / `jsx()` 调用 |
| Vue | `@vue/compiler-sfc` | `.vue` 拆成 render 函数 + `<style>` 抽成 CSS 模块 |
| Svelte | `svelte/compiler` | `.svelte` 编译成命令式 DOM 操作代码 |

伪代码层面，一个框架插件长这样（这正是 demo 01 手写的东西）：

```ts
function frameworkPlugin() {
  return {
    name: 'my-framework',
    transform(code, id) {
      if (!id.endsWith('.myx')) return;        // 只处理本框架的文件
      const js = compile(code);                // 调用编译器
      return { code: js, map: null };          // 把标准 JS 交还给 Vite
    },
  };
}
```

### 2. 注入 HMR 代码：让组件能「热更新」

光把语法编译成 JS 还不够——那只是「能跑」。框架开发体验的灵魂是 **HMR（热模块替换）**：改一个组件，页面对应部分局部更新、**且保留状态**（输入框里的字、计数器的数都还在）。

这套能力 Vite 提供的是「底座」（`import.meta.hot` API + WebSocket 通道，见 01 章 HMR 部分），但**具体怎么用这个底座做到「只换组件、不丢状态」，是框架插件注入的代码实现的**。插件在编译产物末尾自动追加类似这样的样板：

```js
// 由框架插件自动注入，你写组件时看不到它
if (import.meta.hot) {
  import.meta.hot.accept((newModule) => {
    // 框架特定逻辑：用新组件替换旧组件，并尽量保留组件状态
  });
}
```

> 关键结论：**HMR 不是 Vite 单独给的，也不是框架单独给的，而是「Vite 的 `import.meta.hot` 通道」+「框架插件注入的接管逻辑」合作的结果。** 这解释了一个高频困惑——为什么同样用 Vite，React 和 Vue 的热更新行为、能保留多少状态会有差异：因为接管逻辑是各框架插件各写各的。

#### `import.meta.hot` 常用三件事：accept、dispose、prune

`import.meta.hot` 只在 dev 环境存在。框架插件会自动生成它，但你写普通模块、手写插件 demo、或排查 HMR 退化时，最好知道这三个 API 分别解决什么问题。

**1. `accept`：声明“这个更新我能接住”**

最常见的是自接受：模块自己变化时，自己处理。

```js
// counter.js
export let count = 0;

export function inc() {
  count += 1;
}

if (import.meta.hot) {
  import.meta.hot.accept((newModule) => {
    // newModule 是重新 import 后的新 counter.js
    console.log('counter.js updated:', newModule.count);
  });
}
```

也可以接受某个依赖的更新：

```js
import { message } from './message.js';

if (import.meta.hot) {
  import.meta.hot.accept('./message.js', (newMessageModule) => {
    console.log('message changed:', newMessageModule.message);
  });
}
```

这就是 HMR 边界的来源：某个模块说“我能处理自己或某个依赖的变化”，Vite 的更新传播就可以在这里停住。

**2. `dispose`：旧模块被替换前，先清理副作用**

HMR 会重新执行新模块，但旧模块留下的副作用不会自动消失。比如定时器、事件监听、WebSocket 连接、第三方库实例，都应该在 `dispose` 里清理。

```js
const timer = setInterval(() => {
  console.log('tick');
}, 1000);

if (import.meta.hot) {
  import.meta.hot.dispose(() => {
    clearInterval(timer);
  });
}
```

`dispose` 还常和 `import.meta.hot.data` 配合，把状态交给下一版模块：

```js
let count = import.meta.hot?.data.count ?? 0;

export function inc() {
  count += 1;
}

if (import.meta.hot) {
  import.meta.hot.dispose((data) => {
    data.count = count;
  });
}
```

**3. `prune`：模块不再被导入时，清理残留资源**

`dispose` 是“这个模块要被新版本替换了”；`prune` 是“这个模块已经从当前模块图里消失了”。典型场景是样式注入：某个模块曾经插入过 `<style>`，后来 import 被删掉了，如果不清理，页面上会残留旧样式。

```js
const style = document.createElement('style');
style.textContent = '.demo { color: red; }';
document.head.appendChild(style);

if (import.meta.hot) {
  import.meta.hot.prune(() => {
    style.remove();
  });
}
```

可以这样记：

| API | 什么时候触发 | 主要作用 |
|---|---|---|
| `accept` | 模块或依赖变化时 | 声明 HMR 边界，告诉 Vite“我能处理这次更新” |
| `dispose` | 旧模块被新模块替换前 | 清理定时器、事件监听等副作用，也可把状态写入 `hot.data` |
| `prune` | 模块不再被任何地方导入时 | 清理已经离开模块图的残留资源，比如注入的样式 |

### 3. 配套处理：依赖预构建、CSS、文件类型

插件还会顺手配置一些 Vite 行为，让框架开箱即用，例如：

- 声明需要预构建的依赖（如 `react` / `react-dom` / `vue`），避免运行中途触发二次预构建（见 [05 依赖预构建](../01-核心使用/05-依赖预构建.md)）；
- Vue 插件把 SFC 里的 `<style>` 抽成独立 CSS 模块，接入 Vite 的 CSS 管线（见 [04 静态资源与 CSS](../01-核心使用/04-静态资源CSS别名与路径解析.md)）；
- 告诉 esbuild/Oxc 把 `.jsx`/`.tsx` 当 JSX 解析。

## 三、一张图看清集成位置

```
浏览器请求 /src/App.jsx
        │
        ▼
   Vite dev server
        │  resolveId  → 找到文件
        │  load       → 读出源码（仍是 JSX）
        │  transform  ──► 【框架插件在这里接管】
        │                   1. JSX/SFC/svelte → 标准 JS
        │                   2. 注入 import.meta.hot 接管代码
        │                   3. 抽离 <style> 等
        ▼
   返回浏览器能执行的 JS（含 HMR 代码）
        │
        ▼
   改文件 → Vite 经 WebSocket 推送更新 → 注入的 hot.accept 局部替换组件
```

把这张图记住，你就有了排查框架问题的「分层定位」能力：

- **语法/编译报错**（Failed to parse、Unexpected token）→ 第 1 步，插件没装/没匹配到该文件/编译器配置不对。
- **改了不更新、或整页刷新**（HMR 退化）→ 第 2 步，注入的 hot 接管失效（常见原因见下文）。
- **样式不生效 / 闪烁** → 第 3 步，CSS 抽离与注入环节。

## 四、HMR 退化为整页刷新：最常见的「集成」问题

这是框架集成里最高频的实战坑，本质都是「插件的 hot.accept 接管不了这次变更，只能退而求其次刷新整页」。常见诱因：

1. **组件文件里混入了非组件导出**：插件的 Fast Refresh / HMR 接管通常要求一个文件「只导出组件」。如果你在 `Button.jsx` 里又 `export const someConst = 1`，React 插件可能判定无法安全热替换，退化为整页刷新。
   - 解决：把常量/工具函数挪到单独文件。
2. **匿名默认导出**：`export default () => <div/>` 这种匿名组件，插件拿不到稳定名字做状态映射，可能不保留状态。
   - 解决：给组件具名。
3. **改的是「被很多模块依赖的公共文件」**：比如改了一个全局 store 或 `main.ts`，HMR 沿模块图向上找不到能 accept 的边界，最终冒泡到根 → 整页刷新（这属于 HMR 机制本身，不是 bug，[09 工程排障](../01-核心使用/09-真实工程排障专题.md) 有讲）。
4. **插件没正确启用**：`vite.config` 里忘了把插件放进 `plugins`，或装了但版本与 Vite 8 不兼容。

> 排查口诀：**先确认「是编译问题还是热更问题」**——能正常显示、只是改了不局部更新，就是 HMR（第 2 步）；连页面都起不来、报解析错误，就是编译（第 1 步）。

## 五、动手：手写一个「迷你框架插件」

光看概念容易飘。配套 demo 让你**亲手写一个 Vite 插件**，处理自定义的 `.myx` 文件（一个极简「框架」），完整体验上面三件事——编译 + HMR 注入。

配套代码：[第一阶段-使用篇/02-框架集成与测试/01-框架插件集成机制/](https://github.com/XY0987/vite_brochure_code_public/tree/main/第一阶段-使用篇/02-框架集成与测试/01-框架插件集成机制/)

```bash
cd vite_brochure_code_public/第一阶段-使用篇/02-框架集成与测试/01-框架插件集成机制
npm install
npm run dev
```

观察点：

1. `src/App.myx` 是「框架语法」（一段非标准 JS 模板），浏览器本来不认识。
2. `plugins/vite-plugin-myx.js` 是我们手写的插件：在 `transform` 里把 `.myx` 编译成标准 JS，并注入 `import.meta.hot.accept`。
3. 启动后改 `App.myx` 里的文案 → 页面**局部更新且计数器状态保留**（这就是插件注入的 HMR 在起效）。
4. 把插件里注入 hot 的那段代码注释掉、重启，再改文件 → 这次变成**整页刷新、计数器归零**。亲眼对比「有没有插件接管」的差别。

## 六、本节小结

- Vite 不认识框架；`.vue`/`.jsx`/`.svelte` 全靠框架插件在 **`transform`** 钩子里编译成标准 JS。
- 框架插件做三件事：**编译语法、注入 HMR 接管代码、配套处理（预构建/CSS/文件类型）**。
- 框架的「丝滑热更新（局部更新 + 保留状态）」= Vite 的 `import.meta.hot` 通道 + 插件注入的接管逻辑，缺一不可。
- 出问题先分层：解析报错→编译环节（插件没装/不匹配）；改了不更新→HMR 注入环节（混入非组件导出、匿名导出、公共文件冒泡）。

## 七、可直接用于项目的 checklist

- [ ] 用某框架前，确认已装并在 `vite.config.plugins` 里启用了对应 `@vitejs/plugin-*`，且版本与 Vite 8 兼容。
- [ ] 遇到 “Failed to parse / Unexpected token” 先查：插件是否覆盖了这个文件扩展名（如 `.tsx`）。
- [ ] HMR 退化为整页刷新时，先看改的是不是「混入非组件导出 / 匿名导出 / 公共依赖文件」。
- [ ] 组件文件保持「只导出组件」，常量、工具函数拆到独立文件，给 Fast Refresh 留出热替换边界。
- [ ] 区分两类问题：起不来=编译问题，起得来但不热更=HMR 问题，按层定位。
