# 01 · 五个工具各自的定位与擅长场景

> 本节解决的真实工程问题：esbuild、Rollup、Rolldown、webpack、Oxc——这 5 个名字在 Vite 的文档、博客、报错信息里反复出现，新手最容易把它们混成「一堆差不多的打包工具」。一旦混了，你就读不懂「为什么 Vite 8 把 esbuild 换成 Oxc」「Rolldown 和 Rollup 到底什么关系」「webpack 还用得着吗」这类问题。本节给每个工具一个**一句话身份**和**它最擅长的场景**，建立一张干净的「工具地图」，后面两节（关系、选型）都建立在这张地图上。
>
> 事实基线：2026 年中，Vite 8.1.x / Rolldown 1.1.x / Oxc 0.13x。

---

## 一、先分清两个大类：打包器 vs 工具链

把 5 个名字摆上桌前，先立一条最重要的分界线，否则你会拿苹果比橘子：

- **打包器（bundler）**：吃进一堆模块（你的源码 + 依赖），顺着 `import` 关系把它们「打」成少量几个可部署的文件（chunk）。它关心的是**模块图、依赖关系、产物拆分**。esbuild、Rollup、Rolldown、webpack 都是打包器。
- **工具链 / 单点工具（toolchain）**：只负责打包流程里的**某一个环节**——比如「把 TS/JSX 转成普通 JS」（转译）、「把代码压小」（压缩）、「检查代码风格」（lint）。它**不组织模块图**。Oxc 就是这一类。

> **一句话区分：打包器负责「把多个模块拼成产物」，工具链负责「把单个文件处理一下」。** 所以「Oxc 取代 esbuild」这句话要拆开看——在 Vite 内部，Oxc 取代的是 esbuild 原来承担的 **TS/JSX 转译、压缩**等单文件处理能力；真正被 Rolldown 取代的打包主链路是 **Rollup**。至于 esbuild 的打包能力，Vite 过去主要用在 dev 依赖预构建（`optimizeDeps`）里，这部分也随着 Rolldown 统一管线被接管。这个细节后面 02 节会重点讲。

记住这条线，下面逐个看。

## 二、esbuild：极快，但产物控制弱

- **语言**：Go（这是它快的根本原因之一——原生编译 + 高度并行）。
- **类型**：打包器 + 转译器（两个能力都有）。
- **擅长**：**速度**。它的转译（TS/JSX → JS）和打包都比 JS 写的工具快一两个数量级。
- **短板**：**产物控制弱**。代码分割（code splitting）能力有限、对复杂的 tree-shaking 和高级分包策略支持不如 Rollup 精细，CSS / 高级输出格式等场景也偏弱。

它在 Vite 历史里的位置很关键：**Vite 2–7 的 dev 阶段靠 esbuild 做两件事**——① 依赖预构建（把 `node_modules` 里的 CommonJS / 多文件包预打包成 ESM）；② 转译你的 TS/JSX（只转译、不做类型检查，这也是 [01 核心使用 / 07 TypeScript 处理](../01-核心使用/07-TypeScript处理.md) 讲过的「Vite 为什么不报类型错」的原因）。

> 误区澄清：esbuild **没有死**。Vite 8 不再用它，不代表它退出历史舞台——`tsup`、`tsx`、很多 CLI 工具仍以 esbuild 为核心，独立使用时它依然是「最快的转译/打包器」之一。它只是在 **Vite 内部**被 Rust 工具链替下了主力位置。

## 三、Rollup：库 / 生产打包的事实标准

- **语言**：JavaScript。
- **类型**：打包器（专注**生产构建**，不做 dev server）。
- **擅长**：**产物质量**。干净的 ESM 输出、强大的 tree-shaking、成熟稳定的插件生态、对库打包（多格式输出 esm/cjs/umd）极其友好。掘金 / npm 上大量库都用 Rollup 打包。
- **短板**：**慢**。纯 JS 实现，大型项目构建耗时明显;它也只管 build，没有 dev 时的按需服务能力。

Rollup 是 Vite 的「亲爹」之一：**Vite 2–7 的 build 阶段就是 Rollup 驱动的**，Vite 的插件 API 本质上是 Rollup 钩子的超集（这点第一阶段 03 节、第二阶段插件容器会反复用到）。所以「学 Vite 插件 = 大半在学 Rollup 钩子」。

## 四、Rolldown：Rollup 的 Rust 重写，统一 dev + build

- **语言**：Rust。
- **类型**：打包器（目标是**同时**接管 dev 和 build）。
- **擅长**：**Rollup 的产物质量 + 接近 esbuild 的速度**。它在设计上兼容 Rollup 的插件 API，构建比 Rollup 快约 10–30x，并且 dev/build 共用一套引擎。
- **它解决的核心痛点**：消灭 Vite 长期的「双引擎」问题——dev 用 esbuild、build 用 Rollup，两套引擎导致「开发时好好的、构建后行为不一致」的诡异 bug。Rolldown 让 dev 和 build 跑在同一套模块图、同一套管线上。

**Vite 8 把 Rolldown 设为默认唯一打包器**。可以粗暴地理解：Rolldown = 「用 Rust 重写的、又快又能复用 Rollup 生态的 Rollup」。它内部还用到了 Oxc（见下文），二者同属一条 Rust 工具链。

> 关系预告：Rolldown **取代** Rollup 在 Vite build 里的打包主链路，也接管了 esbuild 过去在 dev 里的依赖预构建职责。详见 02 节。

## 五、webpack：老牌全能，生态最厚也最重

- **语言**：JavaScript。
- **类型**：打包器（dev + build 全包，自带 dev server / HMR）。
- **擅长**：**成熟与全能**。loader/plugin 生态是所有工具里最厚的；HMR、code splitting、Module Federation（微前端）这些概念很多都是 webpack 最早普及的；几乎任何刁钻需求都能找到对应 loader/plugin。
- **短板**：**慢、重、配置复杂**。它的工作模式是「先把整个应用全部打包，再提供给浏览器」，项目越大冷启动越慢——这正是当年 Vite 诞生要解决的痛点（见第一阶段 01 节）。配置心智负担也最重。

webpack 不在 Vite 内部，它是 Vite 在「应用构建」这件事上**正在取代的对象**。但要客观：在重度依赖 webpack 专属 loader/plugin 的老项目、或某些高度定制的企业构建里，webpack 仍有现役价值。它不是「错的」，只是在「现代前端应用的开发体验」这条赛道上被 Vite 这套方案超越了。

## 六、Oxc：Rust 工具链，不是打包器

- **语言**：Rust。
- **类型**：**工具链**（一组单点工具：解析器 parser / 转译器 transformer / 压缩器 minifier / 解析器 resolver / 代码检查 linter）。
- **擅长**：**把打包流程里的「单文件处理」环节做到极快**。比如 `oxlint`（Rust 版 ESLint，快几十倍）、Oxc transformer（TS/JSX 转译）、Oxc minifier（压缩）。
- **关键认知**：**Oxc 不打包**。它不组织模块图、不产出 chunk。它是「给打包器当零件用」的——Rolldown 在内部就用 Oxc 做转译和压缩。

**Vite 8 中 Oxc 接管了转译（TS/JSX → JS）与 JS 压缩**，把这两个原本由 esbuild / terser 承担的环节换成了 Rust 实现。所以更准确的说法是：Vite 8 的底层是 **Rolldown（打包）+ Oxc（转译/JS 压缩）** 这套 Rust 组合拳。

> 一个容易被笼统带过的细节：「压缩」分 JS 和 CSS 两块。**JS 压缩是 Oxc**，而 **CSS 压缩默认是 Lightning CSS**（`build.cssMinify` 默认 `'lightningcss'`，也可设回 `'esbuild'`）。所以严格说 Vite 8 的 Rust 工具链是 Rolldown + Oxc + Lightning CSS，本册为聚焦主线，多数地方只强调前两者，但别误以为「压缩全归 Oxc」。

## 七、一张表收口

| 工具 | 语言 | 类型 | 最擅长 | 最大短板 | 在 Vite 8 中 |
|---|---|---|---|---|---|
| esbuild | Go | 打包器+转译器 | 极致速度 | 产物控制弱 | 退场（仅兼容/兜底） |
| Rollup | JS | 打包器（build） | 产物质量、库打包、插件生态 | 慢、只管 build | 退为兼容层 |
| Rolldown | Rust | 打包器（dev+build） | 又快又复用 Rollup 生态、统一引擎 | 仍在成熟中（生态适配） | **默认唯一打包器** |
| webpack | JS | 打包器（dev+build） | 生态最厚、全能 | 慢、重、配置复杂 | 不在 Vite 内（被取代对象） |
| Oxc | Rust | 工具链（非打包器） | 转译/压缩/Lint 极快 | 不打包 | **接管转译/压缩** |

## 八、动手：用同一份源码对比三个打包器

光看表格记不牢，跑一次最直观。配套 demo 把**同一份源码**分别喂给 esbuild / Rollup / Rolldown，同机同输入跑出时间与产物对比。

> 为什么对比 demo 只跑这三个、而不是表里全部五个：**Oxc 是工具链不打包**（单独放在下面的转译/压缩 demo 里看），**webpack 属于另一代「全量打包 + 自带 dev server」的范式、不在 Vite 生态内**，把它塞进同一场「打包器赛跑」反而会误导。所以这里只对比三个**可直接对位**的打包器，webpack/Oxc 的定位用前面的文字与表格讲清即可。

配套代码：[第一阶段-使用篇/06-打包工具横向对比/01-三打包器横向对比/](https://github.com/XY0987/vite_brochure_code_public/tree/main/第一阶段-使用篇/06-打包工具横向对比/01-三打包器横向对比/)

```bash
cd vite_brochure_code_public/第一阶段-使用篇/06-打包工具横向对比/01-三打包器横向对比
npm install
npm run compare   # 三个打包器各打一遍同一份 src，打印耗时 / 产物大小 / chunk 数
```

你会看到类似输出（脚本已做热身 + 取最快值，数字随机器波动，但量级关系稳定）：

```
工具        耗时(ms)   产物(B)   chunk 数  tree-shaking
esbuild     ~1.3       318       1         ✅ 已摇掉 subtract
rolldown    ~0.9       364       1         ✅ 已摇掉 subtract
rollup      ~2.5       459       1         ✅ 已摇掉 subtract
```

观察点：**Rollup（JS 实现）明显最慢**；esbuild（Go）与 Rolldown（Rust）在这种小输入上都已是亚毫秒级、难分伯仲——**项目越大，原生语言对 JS 的速度优势越明显**。三者都把没人用的 `subtract` 摇掉了，说明它们都是会分析模块图的真打包器。这正好对应上面三段「定位」的文字。

```bash
cd vite_brochure_code_public/第一阶段-使用篇/06-打包工具横向对比/02-Oxc转译与压缩

```

观察点：Oxc 输入一个文件、输出一个文件，全程**没有「打包」概念**——它只做转译和压缩，正是「工具链」的样子。

## 九、本节小结

- 先分两类：**打包器**（esbuild/Rollup/Rolldown/webpack，组织模块图、产出 chunk）vs **工具链**（Oxc，只处理单文件）。
- **esbuild**：Go 写，极快但产物控制弱；Vite 2–7 的 dev 预构建+转译主力，Vite 8 退场但独立场景仍活跃。
- **Rollup**：JS 写，产物质量标杆、库打包首选、插件生态成熟；慢、只管 build；Vite 2–7 的 build 引擎。
- **Rolldown**：Rust 写的 Rollup，兼容 Rollup 生态、统一 dev+build、快 10–30x；Vite 8 默认唯一打包器。
- **webpack**：JS 写，生态最厚最全能但慢/重/配置复杂；不在 Vite 内，是 Vite 在应用构建上取代的对象。
- **Oxc**：Rust 工具链（解析/转译/压缩/Lint），不打包；Vite 8 用它接管转译与压缩，与 Rolldown 同属 Rust 组合。

## 十、可直接用于判断的 checklist

- [ ] 看到一个工具，先问它是「打包器」还是「工具链」——别把 Oxc 当打包器、别指望 esbuild 给你 Rollup 级的分包。
- [ ] 听到「esbuild 被取代了」，要分清：Vite 内部的 TS/JSX 转译与 JS 压缩由 Oxc 接管；生产打包主链路被 Rolldown 取代的是 Rollup；esbuild 过去参与的 dev 依赖预构建也被 Rolldown 统一接管。
- [ ] 选库打包工具，优先想 Rollup 系（产物质量）；选极速转译，想 esbuild 系。
- [ ] 看到 Vite 8 报错里出现 `rolldown` / `oxc` 字样，知道这是底层引擎，不是你装错了包。
- [ ] 评估「要不要继续用 webpack」，从「冷启动速度 + 配置心智 + 是否依赖 webpack 专属生态」三点权衡，而不是「新就是好」。
