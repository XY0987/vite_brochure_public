# 专题 04 · 生态连带影响（实现层）：换了引擎，你的插件会怎样

> 本节目标：换打包器/转译器不是「内部优化」，而是会**连带影响整个插件生态**。本节从实现层讲清三件企业升级最关心的事：① 老的 esbuild `onLoad`/`onResolve` 插件为什么失效、Vite 又给了什么兼容；② 依赖 Rollup「内部实现」的插件为什么可能坏；③ `rolldown-vite` 作为迁移隔离层的原理。
>
> 源码基线：Vite 8.1.0。锚点：`packages/vite/src/node/optimizer/pluginConverter.ts`、`config.ts`、`plugins/esbuild.ts`。

---

## 一、为什么「换引擎」一定会波及插件

插件本质是「挂在打包器/转译器钩子上的回调」。所以插件能不能跑，取决于**底层引擎提供的钩子契约**。Vite 8 同时换了两样东西：

- 转译器：esbuild → Oxc；
- 打包器：Rollup（build）/ esbuild（dev 预构建）→ Rolldown。

钩子契约一旦变化，可以先用这张表判断插件风险：

| 你看到的写法 | 它原来靠什么工作 | Vite 8 后的结果 |
|---|---|---|
| 配在 `optimizeDeps.esbuildOptions.plugins` 里的 esbuild 插件 | 依赖 esbuild 预构建时调用 `setup`、`onResolve`、`onLoad` | 预构建改由 Rolldown 执行，esbuild 钩子不能原样挂上去，需要 Vite 做兼容转换 |
| 读取 Rollup 私有方法或内部数据结构的插件 | 不是只用公开插件钩子，而是碰了 Rollup 内部实现 | Rolldown 只兼容公开 API，不保证有这些私有实现，升级后最容易失效 |
| 只使用 `resolveId`、`load`、`transform` 等公开钩子的 Rollup/Vite 插件 | 依赖的是公开插件契约 | 大多可以继续工作，但仍要用实际构建产物验证 |

关键判断标准一句话：**只用「公开钩子契约」的插件大概率没事，碰了「引擎内部实现」的插件容易出事。**

## 二、esbuild 插件的挂载点变化与 Vite 的兼容垫片

### 2.1 为什么不能原样挂载

Vite 8 以前的依赖预构建由 esbuild 完成，所以 Vite 暴露了 `optimizeDeps.esbuildOptions.plugins` 让你塞 esbuild 插件进预构建。esbuild 插件的形状是这样的：

```js
const myEsbuildPlugin = {
  name: 'my-plugin',
  setup(build) {
    build.onResolve({ filter: /^env$/ }, args => ({ path: args.path, namespace: 'env-ns' }))
    build.onLoad({ filter: /.*/, namespace: 'env-ns' }, () => ({ contents: 'export default {}' }))
  },
}
```

Vite 8 预构建改用 **Rolldown**（详见 [专题 02 Rollup vs Rolldown 深度对比](./专题02-Rollup对比Rolldown.md)），Rolldown 不认识 esbuild 的 `setup`/`onResolve`/`onLoad`——这套钩子在新引擎里没有原生挂载点。所以问题不是“老 esbuild 插件一定立刻失效”，而是**它不能再按 esbuild 的方式原样执行**，必须经过 Vite 的兼容转换后才有机会继续工作。

### 2.2 Vite 给的兼容垫片：自动转换为 Rolldown 插件

Vite 8 没有让老插件直接报错，而是写了一个**转换器**，把 esbuild 插件「翻译」成 Rolldown 插件。

调用点：`packages/vite/src/node/config.ts`（L1371–1384）

```ts
function applyDepOptimizationOptionCompat(resolvedConfig: ResolvedConfig) {
  if (resolvedConfig.optimizeDeps.esbuildOptions?.plugins?.length > 0) {
    resolvedConfig.optimizeDeps.rolldownOptions ??= {}
    resolvedConfig.optimizeDeps.rolldownOptions.plugins ||= []
    ;(resolvedConfig.optimizeDeps.rolldownOptions.plugins as any[]).push(
      ...resolvedConfig.optimizeDeps.esbuildOptions.plugins.map((plugin) =>
        convertEsbuildPluginToRolldownPlugin(plugin),   // 🔖断点[专题04] esbuild 插件被翻译成 Rolldown 插件
      ),
    )
  }
}
```

转换器本体：`packages/vite/src/node/optimizer/pluginConverter.ts`（L31）

```ts
export function convertEsbuildPluginToRolldownPlugin(
  esbuildPlugin: esbuild.Plugin,   // 🔖断点[专题04] 把 esbuild 的 onResolve/onLoad 映射到 Rolldown 的 resolveId/load
): RolldownPlugin {
  // 伪造一个 esbuild PluginBuild,收集 onResolve/onLoad 回调
  // 再用 Rolldown 的 options/buildStart/resolveId/load/generateBundle 钩子驱动它们
}
```

它的思路很巧：**伪造一个 esbuild 的 `PluginBuild` 对象**喂给老插件的 `setup(build)`，把它注册的 `onResolve`/`onLoad` 回调收集起来，再用 Rolldown 的 `resolveId`/`load` 钩子在合适时机调用它们——相当于给 esbuild 插件套了个「Rolldown 适配器」。esbuild 的 `namespace` 这种概念也被映射成 Rolldown id 的 `namespace:path` 前缀（见 `idToPathAndNamespace`）。

### 2.3 但兼容是有限的：踩坑预警

转换器**只覆盖最常用的 `onResolve`/`onLoad` + `namespace`**。一旦插件用到 esbuild 的高级能力，转换器里大量分支会直接 `throw new Error('Not implemented')`：

- `build.resolve()`（插件内主动触发解析）→ 未实现，抛错；
- `pluginBuild.esbuild`（拿 esbuild 实例自己调 transform）→ 未实现，抛错；
- `onResolve` 返回 `errors`/`warnings`/`watchDirs`、`onLoad` 返回这些字段 → 未实现，抛错；
- `metafile`、`mangleCache`、`outputFiles` 等构建结果字段 → Proxy 拦截，访问即抛错。

> 现象 → 原因 → 解决：升级后预构建时报 `Not implemented`，**原因**多半是某个 esbuild 插件用了转换器没覆盖的能力。**解决**：优先找该插件的 Rolldown/Vite 原生版本；没有的话，把它从 `optimizeDeps.esbuildOptions.plugins` 里挪走、改用 `optimizeDeps.rolldownOptions.plugins` 直接写 Rolldown 插件。另外 `optimizeDeps.esbuildOptions` 整体已被标记 deprecated（`config.ts:1222` 附近会打印迁移警告，建议改用 `optimizeDeps.rolldownOptions`）。

## 三、依赖 Rollup「内部实现」的插件为什么有问题

这是迁移 Vite 8 时最需要警惕的一类——也是最隐蔽的一类。

Rolldown 兼容的是 Rollup 的**公开插件 API**：`resolveId`、`load`、`transform`、`buildStart`、`renderChunk`、`generateBundle` 等钩子，以及 `this.resolve`、`this.emitFile`、`this.getModuleInfo` 等公开的插件上下文方法（主线 [07 插件容器](../01-Vite实现原理/07-插件容器PluginContainer.md) 讲的就是这套契约怎么被驱动）。

但有些插件为了实现某些功能，**绕过公开 API、直接访问 Rollup 的内部数据结构或私有方法**，例如：

- 直接读写 Rollup 内部的模块/chunk 表的私有字段；
- 依赖 Rollup 某个未文档化的行为顺序或内部对象形状；
- 调用 Rollup 没有对外承诺的内部函数。

Rolldown 是**重新用 Rust 实现**的，它复刻了「公开契约」，但没有义务、也不可能复刻 Rollup 的全部内部实现细节。于是这类插件就会以各种奇怪的方式失效——可能报 `undefined is not a function`，可能静默产出错误产物。

> 判断与应对：升级前先盘点插件，重点排查那些「做高级产物操作、明显超出标准钩子能力」的插件（常见于一些深度定制 chunk、改写产物结构的插件）。官方与社区在 Rolldown 化过程中已为大量主流插件提供了适配版本——优先升级到适配版，而不是自己 hack。这也呼应第三阶段「抽象的代价与收益」：插件容器复用 Rollup 生态带来了兼容红利，但「兼容公开契约 ≠ 兼容内部实现」正是这层抽象的边界与约束。

## 四、`rolldown-vite`：迁移隔离层的原理

直接把全世界的 Vite 项目一夜之间切到 Rolldown，风险太大。社区的做法是先提供一个**隔离层包**：`rolldown-vite`。

它的原理（实现层）可以概括为「**同一份 Vite，换掉底层打包器依赖**」：

- `rolldown-vite` 是 Vite 的一个**drop-in 替代包**：API、配置、行为尽量和官方 Vite 对齐，但底层把 Rollup 换成了 Rolldown。
- 接入方式通常是用包管理器的 **alias/override**，把项目里对 `vite` 的依赖指向 `rolldown-vite`，源码和 `vite.config` 基本不动。
- 这样形成一个「试验隔离层」：想试 Rolldown 就切到 `rolldown-vite` 验证，发现问题随时切回官方 `vite`，**升级与回滚都只是改一行依赖别名**。

它的工程价值，正是第三阶段「渐进式演进」的活案例：**用一个隔离包把「换打包器」这件高风险的事，变成可灰度、可回滚的开关**，而不是一次不可逆的大爆炸式迁移。等 Rolldown 在足够多真实项目里验证成熟（即 Vite 8 把它设为默认的前提），隔离层的历史使命也就完成了。

> 事实基线说明：到 2026 年中，Rolldown 已随 Vite 8 成为默认引擎、`rolldown-vite` 主要承担「从旧版 Vite 渐进迁移」的过渡角色。具体包名/接入细节随版本演进，迁移前请以对应版本的官方迁移指南为准——这是一个阶段性工具，不要当成永久结论。

## 五、一张「升级影响 checklist」

把本专题四节的结论收敛成一份可直接用于项目评估的清单：

- [ ] **盘点 esbuild 插件**：项目是否用了 `optimizeDeps.esbuildOptions.plugins`？用了哪些高级能力（`build.resolve`、自定义 errors/warnings）？→ 高风险，优先找 Rolldown 原生替代。
- [ ] **盘点「魔改型」插件**：是否有插件深度操作产物 chunk、依赖 Rollup 内部行为？→ 升级到适配版，或在产物上重点验证。
- [ ] **配置项迁移**：`rollupOptions` 可留（已被代理为 `rolldownOptions`），但 `manualChunks` 等要在产物上验证分包；`esbuild: false` 改成 `oxc: false`；`optimizeDeps.esbuildOptions` 改 `optimizeDeps.rolldownOptions`。
- [ ] **压缩器**：默认已是 Oxc；若强依赖 terser/esbuild 压缩特性，显式 `build.minify: 'terser' | 'esbuild'` 并安装对应可选 peer 依赖。
- [ ] **灰度策略**：大型项目优先用 `rolldown-vite` 隔离层灰度验证，再切官方默认，保留一键回滚。
- [ ] **产物验证**：升级后务必跑一次真实生产构建并比对产物（体积、分包、运行时行为），不要只看 dev/preview 正常（呼应主线 [Vite实现原理/12-preview-server边界](../01-Vite实现原理/12-preview-server边界.md)）。

## 六、本节小结

**这套兼容设计解决了什么问题？**
它让「换引擎」这件事对大多数存量项目尽量无感：esbuild 插件被自动翻译成 Rolldown 插件、`rollupOptions` 被代理、`esbuild` 配置被转成 `oxc`、`rolldown-vite` 提供可回滚的灰度隔离层——共同把一次激进的底层替换，包装成一条可渐进、可回滚的升级路径。

**它带来了什么复杂度 / 代价？**
兼容是有边界的：esbuild 插件转换器只覆盖常用钩子，高级能力直接抛 `Not implemented`；「兼容公开契约」救不了依赖 Rollup 内部实现的插件；这些兼容层本身（转换器、代理、隔离包）都是必须长期维护、且会随版本演进的「技术债式资产」。这正是第三阶段「性能与可维护性的边界」要讨论的：用 Rust 重写换来的速度，代价之一就是这一整套生态适配工程。

**读完你应当能做到：**

- [ ] 用「公开契约 vs 内部实现」这把尺子，判断一个插件升级到 Vite 8 的风险；
- [ ] 解释 esbuild 插件失效的原因，以及 `convertEsbuildPluginToRolldownPlugin` 兼容垫片的原理与边界；
- [ ] 说清依赖 Rollup 内部实现的插件为何会坏，以及应对策略；
- [ ] 理解 `rolldown-vite` 作为迁移隔离层「换底层依赖、可灰度可回滚」的原理；
- [ ] 拿着第五节的 checklist 评估一个真实项目的 Vite 8 升级影响面。
